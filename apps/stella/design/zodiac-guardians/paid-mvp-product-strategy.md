# 유료 카드 리포트 MVP와 확장 전략

별자리 수호령 카드 리포트의 상품 구조, 가격, 추첨, 계정, 결제, 성장 루프를 한곳에 기록한다.
캐릭터 외형과 원화 규칙은 [캐릭터 바이블](./character-bible.md), 장면 목록은
[카드 카탈로그](./card-catalog.md)를 기준으로 한다. 현재 화면과 한국 첫 결제 구현은
[한국 전체 리포트 결제·공개 수직 슬라이스](./korea-paid-report-vertical-slice.md)를 따른다.

## 문서 상태

- 마지막 갱신: 2026-08-03
- 서비스 중심: 앞으로도 웹
- 출시 순서: 한국 → 중국 본토 → 이후 미정
- `확정`: 사용자가 명시적으로 결정한 내용
- `권장안`: 출시 전에 수치 또는 세부 동작을 최종 승인해야 하는 현재 추천값
- 구현 상태: 상품 매니페스트·추첨·게스트 컬렉션·리포트·구매·획득·보장과 유료 질문의 Worker 번들
  콘텐츠 계약·실제 한국어 선택형 44개와 선택 메모 1개·답변별 진행·마지막 답변의 카드 fulfillment,
  중앙 PortOne 연동, 공개 랜딩과 분리된 무료 검사·무료 결과·유료 검사·유료 결과, checkout·질문·리포트 API,
  staging·production schema, 공용 scheduler 기반 pending 재조정과 30일 미결제 정리,
  결제 완료 메일과 15분 1회용 재열람 링크 교환, 사랑 카드 재추첨 checkout·결제 확정·크레딧·추첨·
  보관함·명시적 대표 카드 선택 UI/API, 중앙 accounts Worker와 Stella OIDC session·게스트 collection 귀속·
  계정 보관함·account-save 보상까지 코드 구현. 통합 계정 인프라 apply와 schema push·고정 client bootstrap,
  production 1,024장 카탈로그는 후속 작업

## 1. 목표와 제품 원칙

### 확정 목표

사용자 행동 목표의 우선순위는 다음과 같다.

1. 매일 재방문
2. 공유
3. 댓글
4. 결과 끝까지 읽기

사업 목표는 참여율과 재방문율을 해치지 않는 범위에서 매출과 첫 결제 전환을 극대화하는 것이다.
초기 핵심 고객은 한국, 중국, 일본, 미국의 여성으로 보되 연령은 아직 가정하지 않는다.

### 제품 원칙

- 첫 가치는 개인화된 해석이고, 카드는 그 해석을 소장하고 다시 방문하게 만드는 자산이다.
- 전체 리포트의 가격은 카드 장수만으로 설명하지 않는다.
- 재추첨은 사용자가 “디지털 랜덤 카드 한 장”으로 비교하므로 낮은 진입 가격이 중요하다.
- 희귀도는 해석의 정확성, 긍정성, 중요도와 연결하지 않는다.
- 전 세계 수천 장을 하나의 완성 목표로 보여주지 않고, 사용자가 이해할 수 있는 작은 앨범으로 나눈다.
- 웹 리포트가 원본이다. 3:4 카드 다운로드와 공유 이미지를 제공하고 PDF는 선택적 내보내기로만 고려한다.

## 2. 한국 유료 MVP 상품

### 확정 구성

첫 구매는 네 주제를 모두 다루는 하나의 전체 리포트다.

| 순서 | 슬롯     | 유료 MVP 카드                               |
| ---- | -------- | ------------------------------------------- |
| 1    | 자기이해 | 게시된 단일 패밀리의 단일 에디션            |
| 2    | 사랑     | 게시된 단일 패밀리의 네 희귀도 중 한 에디션 |
| 3    | 일       | 게시된 단일 패밀리의 단일 에디션            |
| 4    | 결정     | 게시된 단일 패밀리의 단일 에디션            |

- 유료 MVP는 현재 대표 원화와 같은 4개 패밀리·7개 실제 에디션으로 시작한다. 자기이해·일·결정은
  각각 단일 후보이고, 사랑 한 패밀리만 Orbit·Nebula·Eclipse·Stella 네 단계 희귀도를 무작위
  추첨한다.
- 무료·유료 답변은 MVP의 네 주제 상세 리포트 본문, 섹션별 해석 초점과 한 줄 메시지를 실질적으로
  바꾼다. 게시 패밀리가 슬롯마다 하나뿐이므로 MVP에서는 사랑 희귀도 이외의 원화가 입력으로
  바뀌지는 않는다.
- production에서는 같은 후보 선택 계약에 패밀리와 에디션을 추가하고, 출생 차트와 질문 답변에
  따라 네 슬롯의 기본 패밀리와 원화가 달라지게 한다.
- 최초 유료 결과는 서버가 저장한 선택 컨텍스트·카드·렌더된 본문 스냅샷으로 만든다. 이후 결과
  조회는 서버에 명시적으로 걸어 둔 획득 카드만 합성하며 브라우저가 카드를 임의로 바꾸지 않는다.
- production 정식 출시 시점에는 실제로 획득 가능한 3:4 에디션을 최소 1,024장 게시한다.
  `1,024`는 패밀리 수와 곱하는 숫자가 아니라 준비가 끝난 실제 일러스트의 총수다.
- 질문 답변과 출생 차트는 사랑 희귀도 확률에는 영향을 주지 않는다.
- 첫 구매 이후에는 전체 리포트를 다시 결제시키지 않고 사랑 카드만 저가로 재추첨할 수 있다.
- 사랑 카드 재추첨에서는 일러스트와 카드의 한 줄 메시지만 바뀐다.
- 이미 구매한 사랑 해석 본문과 나머지 세 카드의 해석은 바뀌지 않는다.
- 새 사랑 카드는 획득 즉시 게스트 보관함에 추가하지만 현재 리포트에는 자동으로 적용하지 않는다.
  사용자가 `이 카드를 리포트에 걸기`를 눌렀을 때만 대표 사랑 카드가 바뀐다.
- 전체 리포트 구매 때 만든 게스트 보관함과 구매 이메일 재열람 권한으로 재추첨도 구매·사용할 수 있다.
  계정 생성은 재추첨 결제의 선행 조건이 아니다.
- 카드 원화는 3:4만 사용한다. 카드 뒷면, 프레임, 이름, 제목, 배지는 앱 UI에서 합성한다.
- 출시 뒤 후보가 늘어나도 같은 선택 계약과 결과 형식을 유지한다.

### 확장 상품 단위

- 새로운 질문이나 새로운 기준 시점으로 전체 리포트를 만들면 새 전체 리포트 상품이다.
- 같은 전체 리포트에서 다시 뽑는 것은 사랑 카드 에디션 재추첨 상품이다.
- 계절, 의상, 배경이 늘어나도 사용자가 처음 받은 기본 장면의 의미는 유지한다.
- 장기 후보인 다섯 번째 `숨은 동행자` 슬롯은 현재 한국 출시 상품에 포함하지 않는다.

### 무료 미리보기와 유료 질문

- 현재 두 질문인 `원하는 답의 온도`와 `현재의 움직임`은 무료 미리보기에서 받는다.
- 무료 결과는 잠금 목록만 보여주는 한 줄 티저가 아니다. 두 답을 함께 해석한 현재 마음, 기존 무료
  출생 차트의 Big 3·원소 단서, 답 조합별 오늘의 작은 행동과 성찰 질문까지 약 1분 분량의 작은
  완결 리포트로 제공한다.
- 무료 결과는 사용자가 개인화 품질을 판단할 만큼 구체적이어야 하지만 자기이해·사랑·일·결정의
  주제별 상세 본문, production 카드 패밀리·에디션·희귀도와 실제 원화는 공개하지 않는다. 유료
  가치는 무료 문장의 잠금 해제가 아니라 16~20개 추가 답으로 만드는 네 주제의 깊이와 카드 소장에 둔다.
- Stella 앱에서는 결제 전 유료 질문 원문을 표시하지 않는다. 대신 질문 수 범위, 네 주제를 모두
  다룬다는 점, 예상 소요시간, 중간 저장과 재개 가능 여부를 명확히 보여준다.
- 복구 이메일을 받은 뒤 PortOne 결제를 열고, 서버가 원격 결제 상태와 금액을 확인해 `paid`
  entitlement를 만든 다음에만 유료 질문을 제공한다.
- 결제 후 질문은 네 주제별 핵심 맥락을 묻는 12개와 주제별 필수 맞춤 질문 1개씩을 제공한다.
  누적 답변이 설정 기준을 넘긴 주제에는 심화 질문을 하나씩 더해 총 `16~20개`를 출제한다.
  풍부함은 모든 사람에게 같은 긴 문항을 강제하는 대신 관련 있는 심화 질문으로 만든다.
- 필수 문항은 모두 선택지 기반으로 구성한다. 자유 입력은 16~20개 진행률이 끝난 뒤 별도 선택
  메모로 한 개만 제공하며, 작성하지 않아도 카드 공개와 리포트 완성을 막지 않는다.
- 16~20개 답변은 카드 한 줄에만 쓰지 않고 네 주제의 상세 본문, 섹션별 해석 초점과 전체 요약을
  실질적으로 바꾼다.
- 장기적으로 50~150개를 준비하더라도 이는 모든 구매자에게 전부 묻는 수가 아니라 적응형 출제를
  위한 문항은행의 크기다. 사용자별 실제 출제 수는 별도 제품 검증 없이 20개를 넘어
  자동 확대하지 않는다.
- 질문 진행은 답변마다 서버에 저장하고 복구 이메일의 재열람 경로에서 이어서 할 수 있게 한다.
  질문을 마친 뒤에만 카드 패밀리와 에디션을 선택하고 결과를 `fulfilled`로 고정한다.
- 구매 상태는 기존 `pending → paid`를 사용하고, 결제 후 미완료 질문은 `guardian_report.draft`로
  표현한다. `awaiting_questions` 같은 중복 상태를 별도로 추가하지 않는다.

#### 유료 질문 소스와 전달 경계

- 유료 질문의 원문, 선택지, 적응형 선택 정책과 점수 행렬은
  `apps/stella/content/guardian-questionnaires`의 locale별 JSON으로 Git에 커밋한다.
- 이 repository는 public이므로 Git 원본은 repository 독자에게 공개된다. 결제 entitlement는
  Stella 앱/API의 질문 접근을 제어하며 Git 원본을 비밀로 만드는 장치가 아니다.
- 질문 JSON은 Database Worker의 서버 전용 번들에 포함한다. PostgreSQL에는 질문 콘텐츠를 저장하지
  않고 Next의 `src`나 정적 `public`에서도 JSON을 import하지 않는다.
- 브라우저는 전체 질문 은행이나 임의 ID 목록을 받지 않는다. 결제가 확인된 questionnaire
  session에 현재 한 문항만 표시하고, 답변 저장 응답에 다음 유효 문항을 함께 반환하는 방식을
  기본 권장안으로 둔다.
- 질문별 컬럼이나 `if MVP` 분기를 만들지 않고 안정적인 문자열 `questionId`·`optionId`와
  `questionId → { type: "option", optionId } | { type: "text", text: string | null }` 답변 map을 저장한다.
- 앱의 목표는 질문 원본에 DRM을 거는 것이 아니라 정상 구매 흐름에서 결제 뒤 관련 문항만
  순서대로 제공하고, 전체 은행을 정적 export나 일반 API 응답으로 불필요하게 전달하지 않는 것이다.

## 3. 고정 프로토타입에서 변동 상품으로 확장하는 방법

프로토타입 전용 상품 분기를 만들지 않고 유료 경로에서는 처음부터 동일한 선택 파이프라인을
사용한다.

```text
출생 입력·무료 답변 2개
  → 선택 컨텍스트 정규화
  → 복구 이메일과 pending 구매 생성
  → 서버가 결제 확인
  → paid questionnaire session
  → 유료 선택형 답변 16~20개 저장
  → 상품 매니페스트에서 유효 후보 조회
  → 점수와 가중치 계산
  → 기본 카드 패밀리·에디션 선택
  → 구매 결과 스냅샷 저장
```

### 프로토타입, 출시, 확장의 차이

- 현재 프런트엔드 프로토타입은 완성된 원화 네 패밀리만 직접 참조한다.
- 유료 MVP는 같은 매니페스트 계약에 4개 패밀리·7개 에디션을 게시한다.
- production 출시 매니페스트에는 실제 에디션을 최소 1,024장 게시한다.
- MVP에서 production으로 갈 때 같은 매니페스트 계약에 카드 패밀리와 에디션을 추가한다.
- 호출부와 결과 형식은 바꾸지 않고 후보 수와 점수 규칙만 확장한다.
- `if prototype`, `if fixedCard` 같은 별도 유료 런타임 경로를 만들지 않는다.

모든 슬롯은 공통 `familyPool`, 모든 패밀리는 공통 `editionPool`을 가진다. 풀의 선택 정책은
다음 세 종류만 데이터로 표현한다.

- `single`: 출시 시 자기이해·일·결정처럼 게시된 에디션이 한 장인 패밀리
- `context_scored`: 차트·질문·계절·의상 태그로 패밀리나 에디션을 안정적으로 선택
- `weighted_random`: 사랑 희귀도처럼 결제 확인 뒤 가중치로 추첨하는 패밀리

`single`은 한 후보짜리 풀일 뿐 고정 카드 전용 코드 경로가 아니다. production에서 후보를 늘릴
때 같은 풀에 후보와 태그를 게시하고 정책을 `context_scored`로 바꾸며, 리포트·구매·획득
스키마는 바꾸지 않는다. 사랑의 최초 카드와 재추첨은 모두 같은 `weighted_random` 에디션 풀을
사용한다.

### 출시 선택 규칙 권장안

- 자기이해는 태양 별자리와 같은 캐릭터를 고정 축으로 두고 달과 상승궁은 장면·문구에 반영한다.
- 사랑은 금성을 중심으로 하고, 출생 시간이 정확할 때만 7하우스·디센던트를 추가한다.
- 일은 중천점과 토성, 결정은 수성과 화성을 중심으로 한다.
- 현재 프로토타입의 두 답변은 모든 슬롯의 문체·움직임에 사용하고, 결제 후 주제별 답변은 해당
  슬롯의 상세 본문, 해석 초점, 장면 태그와 한 줄에 더 큰 가중치로 사용한다. MVP의 단일 후보
  풀에서는 패밀리가 바뀌지 않고, production의 확장된 풀에서 후보 점수에도 반영한다.
- 차트 관련성을 기본 축으로 유지하되 결제 후 질문의 주제별 맥락은 무료 공통 답변보다 강하게
  반영한다. 정확한 점수 행렬은 유료 questionnaire JSON과 함께 Worker 서버 콘텐츠로 배포한다.
  답변은 실제 선택에 영향을 주지만 답 하나를 바꿀 때마다 반드시 모든 카드가 바뀐다고 약속하지 않는다.
- 자기이해는 태양 별자리 패밀리를 유지하고 추가 답변을 장면·한 줄·해석의 초점에 사용한다.
- 동일한 배포 코드·정규화 입력에는 같은 기본 패밀리가 나오도록 후보 순서로 안정적으로
  동률을 해소한다. 무작위성은 사랑 희귀도·에디션 추첨에만 사용한다.
- 출생 시간을 모르는 사용자는 하우스·각도 값을 추정하지 않고 신뢰 가능한 행성 값만으로
  후보를 선택한다.

### 과도한 방어 로직을 피하는 원칙

- 게시되는 상품 매니페스트는 모든 슬롯에 최소 한 개의 유효 후보가 있는지 게시 시점에 검증한다.
- 존재하지 않는 후보, 원화, 로케일 문구, 확률 합계 오류는 요청 중에 다른 카드로 조용히 대체하지 않는다.
- 잘못된 상품 카탈로그는 배포하지 않는 것이 기본 방어선이다.
- 무료 미리보기는 저장하지 않으므로 `preview` 서버 report 상태를 추가하지 않는다. checkout에서
  pending 구매와 함께 `draft`를 만들고, 결제 확인 뒤 같은 상태에 유료 질문의 저장·재개를 포함한다.
- 질문은 선택 답변과 자유 입력을 구분하는 map 하나로 저장한다. MVP용 답변 컬럼과
  production용 답변 컬럼을 따로 만들지 않는다.
- 같은 구매를 다시 열 때는 현재 규칙으로 재계산하지 않고 저장된 결과를 읽는다.
- 재추첨은 최초 전체 리포트에 고정된 사랑 카드 패밀리 안에서만 에디션을 다시 뽑는다.
- 기본 카드 선택 결과와 입력 컨텍스트를 저장하고, 희귀도는 서버의 별도 난수 추첨으로 결정한다.
  완료된 결과를 과거 선택 코드로 다시 계산하지 않는다.
- 출생 차트와 질문은 카드의 관련성과 기본 장면을 바꾸지만 희귀도 당첨 확률은 바꾸지 않는다.

### 구매 결과 스냅샷

수동 버전 대신 다음 사실을 발생 시점에 직접 고정한다.

- 선택된 네 `cardFamilyId`
- 선택된 네 `cardEditionId`
- 선택에 사용한 출생 차트와 질문 답변 스냅샷
- 렌더가 끝난 locale별 리포트 본문과 카드 표시 스냅샷
- 결제 SKU·상품명·통화·금액과 지급할 entitlement 스냅샷
- 각 카드 획득 당시 후보 에디션·가중치·가중치 합·보장 간격과 실제 적용 여부

이후 규칙, 문구, 확률, 원화가 바뀌어도 과거 구매 결과는 다시 계산하지 않는다. 변경 이력은 Git과
배포 이력으로 추적하고, 이미 게시한 카드의 의미를 바꿀 때는 새 에디션 ID를 만든다.

## 4. 카드와 컬렉션 모델

### 개념 단위

| 단위               | 의미                                                            |
| ------------------ | --------------------------------------------------------------- |
| 카드 패밀리        | 별자리, 주제, 중심 상황이 같은 기본 카드                        |
| 카드 에디션        | 실제로 존재하는 희귀도·계절·의상·배경·연출 원화                 |
| 드로우 풀          | 특정 상품과 시점에 추첨 가능한 에디션 목록과 확률               |
| 앨범               | 사용자가 완성을 시도할 수 있는 제한된 컬렉션                    |
| 보유 카드          | Stella 계정이 획득한 에디션                                     |
| 리포트 스냅샷      | 구매 결과의 패밀리, 에디션, 렌더된 해석을 고정한 읽기 전용 결과 |
| 미보유 보장 카운터 | 다음 미보유 보장까지 남은 유료 재추첨 횟수                      |

희귀도, 계절, 의상 값을 조합해 존재하지 않는 카드를 자동 생성하지 않는다. 실제 원화와 문구가
준비된 조합만 명시적인 `cardEdition`으로 등록한다.

### 수천 장을 보여주는 방법

수천 장은 전체 카탈로그의 크기이자 마케팅 메시지이지 하나의 완성 진행률이 아니다.

- 마케팅: `수천 가지 별의 모습 중 발견된 당신의 카드`
- 현재 카드 패밀리: `사랑의 수호령 2/4`
- 시즌 앨범: `별빛 피크닉 7/24`
- 전체 화면: 패밀리 또는 시즌별 앨범을 탐색
- 피해야 할 표현: `전체 2/3,000`

한 앨범은 처음에는 12~24장 정도로 제한하는 권장안이다. 실제 완성 행동을 본 뒤 앨범 크기를
조정한다.

## 5. 확률, 중복, 미보유 보장

### 확정 원칙

- 중복 획득을 허용한다.
- 일정 횟수마다 미보유 카드를 보장한다.
- 첫 구매부터 보유 상태는 `guardian_collection`에 귀속한다. 처음에는 게스트 capability와 구매 이메일로
  접근하고, 계정 생성 뒤에는 같은 collection을 Stella 계정이 인수한다.

### 유료 MVP 확정안

| 희귀도  | 확률 |
| ------- | ---: |
| Orbit   |  55% |
| Nebula  |  30% |
| Eclipse |  12% |
| Stella  |   3% |

- 최초 전체 리포트의 사랑 카드 추첨은 유료 재추첨 보장 카운터에 넣지 않는다.
- 유료 재추첨 다섯 번째마다 현재 패밀리의 미보유 에디션을 한 장 보장한다.
- 미보유 에디션이 여러 장이면 원래 확률을 남은 에디션끼리 다시 정규화해 추첨한다.
- 네 에디션을 모두 보유했다면 다섯 번째도 일반 확률로 추첨한다.
- 단품 재추첨과 5회권 사용은 같은 유료 카운터를 누적한다.
- 최초 전체 리포트와 이후 사랑 카드 재추첨은 같은 카드 패밀리의 보유 상태를 공유한다.
- 새로운 카드 패밀리를 얻으면 그 패밀리의 수집과 보장 카운터가 별도로 시작된다.
- UI에 `미보유 확정까지 2회`처럼 남은 횟수를 계속 표시한다.

MVP의 보장 범위는 `guardian_collection × 카드 패밀리`로 둔다. 계정 귀속은 같은 collection을
연결하므로 진행률이 초기화되지 않는다. DB에는 순환값 대신 누적 유료 추첨 횟수를 저장하고 현재
보장 간격으로 나머지를 계산한다. 실제 획득 행에는 당시 보장 간격과 적용 여부를 함께 저장한다.
시즌 앨범이 여러 개 생길 때도 스키마를 갈아엎지 않도록 내부적으로는 `guaranteeScopeId`를 두고,
MVP에서는 카드 패밀리 ID를 사용한다. 장기적으로 앨범별 보장이 더 적합한지는 실제 수집 행동을 보고
결정한다.

## 6. 가격

사랑 카드 재추첨이 새 해석 본문을 제공하지 않고 일러스트와 한 줄만 바꾸는 것으로 확정됐기 때문에,
초기 가격은 낮은 디지털 카드 가격에 맞춘다.

- 결제 전환율 하나가 아니라 `유효 미리보기 방문자당 매출`과 `첫 결제자 30일 매출`로 판단한다.

## 7. 구매, Sobok 계정, 저장

### 권장 구매 흐름

```text
무료 차트 + 미리보기 질문 2개
  → 가격이 보이는 구매 선택
  → 결제 직전 복구 이메일 입력
  → 회원가입 없는 첫 결제
  → 서버 결제 확인과 유료 질문 잠금 해제
  → 유료 개인화 선택형 질문 16~20개
  → 카드 선택과 즉시 공개
  → 게스트 보관함과 구매 이메일 재열람으로 결과 보존
  → 사랑 카드 재추첨 결제·획득
  → 새 카드는 보관함에 추가, 선택 시에만 리포트 대표 카드 교체
  → 획득 직후 소복 계정 보관 제안
  → 계정 생성 시 기존 게스트 collection을 그대로 귀속
```

- 첫 결제 전에 회원가입을 강제하지 않는다.
- 유료 질문의 개수 범위와 예상 소요시간은 결제 전에 알리되 원문은 결제 확인 뒤 제공한다.
- 결제 성공과 질문 시작 사이에 계정 생성을 끼워 넣지 않는다.
- 계정 보관은 첫 카드 공개 또는 재추첨 획득처럼 사용자가 가치를 확인한 직후 제안한다. 게스트 구매와
  재추첨은 계정 생성 없이 끝까지 가능해야 한다.
- 게스트 이메일은 결제 직전 필수로 받으며 “영수증과 재열람 링크용, 계정 생성 아님”을 입력란
  바로 아래에 표시한다.
- 게스트 구매는 복구 가능한 구매 접근 토큰과 이메일 전달 상태를 가진다.
- 결제 후 계정을 만들면 게스트 구매, 보유 카드, 보장 카운터를 그 Sobok 계정의 OIDC identity에
  연결한다. 이메일이나 username을 소유권 병합 키로 사용하지 않는다.

`소복 계정에 보관하면 첫 미보유 사랑 카드 재추첨 1회`는 계정 전환과 수집 방법 학습을 위한
실험 후보다. 적용한다면 이 무료 추첨은 유료 보장 카운터에 포함하지 않는다.

### Sobok 통합 계정과 Stella 세션

- 중앙 계정 원장, 인증 비밀과 로그인 UI는 `accounts.sobok.cc`의 `apps/accounts` Worker가 소유한다.
- Stella는 고정 confidential OIDC client이며 authorization code + PKCE `S256`으로 로그인한다.
- 중앙 계정과 Stella의 쿠키는 각각 host-only로 두고 `.sobok.cc` 공유 쿠키를 만들지 않는다.
- Stella Worker가 앱별 세션, 공개 nickname, 구매, 카드, 리포트의 `stella` 데이터 경계를 유지한다.
- 앱 데이터는 중앙 계정을 OIDC `(issuer, sub)`로 식별하고 이메일이나 username으로 연결하지 않는다.
- 중앙 계정의 초기 인증 수단은 비밀번호·전역 username, Google, Kakao, magic link, passkey이며
  비밀번호/username 로그인에만 TOTP를 자동 적용한다.
- 전화번호는 첫 구매의 필수 입력으로 두지 않는다.
- 한국 사용자가 결제·리포트 알림을 카카오톡으로 받겠다고 선택한 경우에만 구매 후 전화번호를 받는다.
- 중국 본토의 계정 제공자와 결과 전달 채널은 아직 미정이다.

상위 경계와 client 운영 계약은 [Sobok 통합 계정 아키텍처](../../../../docs/architecture/sobok-account.md)를
따른다.

### 출생 정보 저장

사용자가 `계정에 보관하기`를 선택하면 출생일, 출생 시간, 출생 장소를 서버에 저장할 수 있다.

편집 가능한 계정 프로필과 구매 결과 스냅샷을 분리한다.

| 저장 단위   | 내용                                                                 |
| ----------- | -------------------------------------------------------------------- |
| 출생 프로필 | 사용자가 입력한 날짜·시간·장소, 정규화 장소 ID, 좌표, 당시 시간대    |
| 파생 차트   | 계산된 차트 핵심값과 정규화된 천문 입력                              |
| 질문 답변   | 상품에 사용한 영구 question·option ID와 완료 시점 답변               |
| 구매 스냅샷 | 결제 조건, 선택된 카드, 렌더된 해석, 획득 당시 후보·가중치·보장 정책 |

사용자가 나중에 출생 프로필을 수정해도 이미 구매한 리포트는 다시 계산하지 않는다. 수정된 프로필은
그다음 새 리포트부터 사용한다.

## 8. 리포트, 공유, 댓글, 재방문

### 리포트 형식

- 원본은 모바일 우선의 인터랙티브 웹 리포트다.
- 카드 공개, 주제별 읽기 진행률, 컬렉션 저장, 공유, 댓글을 한 흐름에 둔다.
- 카드 한 장은 3:4 이미지로 다운로드할 수 있다.
- 공유 링크는 같은 카드 또는 공개 가능한 축약 결과로 연결한다.
- PDF는 보관 요청이 실제로 확인될 때 선택적 내보내기로 추가한다.

### 성장 루프

- 완독: 네 섹션의 진행률과 마지막 종합 문장을 사용한다.
- 공유: 소장하고 싶은 3:4 카드와 한 줄을 먼저 보여주고 공유 링크를 제공한다.
- 댓글: 같은 카드 패밀리 또는 에디션을 받은 사람끼리 대화하도록 주제를 고정한다.
- 재방문: 계정 컬렉션, 미보유 보장 진행률, 새 시즌 앨범을 다음 방문 이유로 사용한다.
- 무료 일일 콘텐츠를 추가한다면 유료 수집 카드 자체를 매일 무료 발급하지 않고, 보유한 수호령의
  짧은 일일 메시지처럼 컬렉션 가치를 떨어뜨리지 않는 형태로 분리한다.

### 한국 채널의 역할 분리

- Kakao 로그인: Sobok 중앙 계정의 인증 수단
- 카카오 공유: 사용자가 직접 실행하는 결과 공유
- 알림톡: 결제와 리포트 복구 같은 거래성 전달
- 카카오 채널 메시지: 재방문 마케팅
- 이메일: 영수증, 게스트 구매 복구, 계정 복구

## 9. 한국과 중국 본토 결제

### 공통 결제 원칙

- 브라우저의 결제 성공 콜백이나 리디렉션만으로 카드를 지급하지 않는다.
- 서버가 결제 ID, SKU, 금액, 통화, 주문 상태를 확인한 뒤 구매 권한을 확정한다.
- 웹훅은 중복 수신돼도 한 번만 반영되는 멱등 처리를 한다.
- 주문과 결제에는 `pending`, `paid`, `failed`, `cancelPending`, `cancelled`처럼 비동기 상태를
  표현할 수 있어야 한다.
- 기본 카드 패밀리는 서버가 `paid`를 확인하고 유료 질문을 모두 받은 뒤 안정적으로 선택한다.
- 사랑 희귀도·에디션 추첨은 유료 질문 완료 뒤 한 번만 실행한다. 질문을 다시 열거나 결제 확인을
  재시도해도 저장된 결과를 반환한다.
- 재추첨권 사용, 보장 카운터 변경, 에디션 추첨, 보유 카드 반영도 하나의 서버 트랜잭션으로 묶는다.

현재 repo에서는 다음 구현을 결제 흐름의 참고 자료로 사용할 수 있다.

- 게스트 체크아웃 생성:
  `apps/vibe/worker/api/deep-type/checkout/POST.ts`
- 결제 확인과 재조정:
  `apps/vibe/worker/payments/confirm.ts`,
  `apps/vibe/worker/payments/reconcile.ts`
- 중앙 PortOne 웹훅과 제품 이벤트 라우팅:
  `apps/payments/worker/index.ts`, `apps/vibe/worker/payments/events.ts`
- 구매 결과 재열람 메일:
  `apps/vibe/worker/lib/reopen-email.ts`

동작 패턴은 재사용하되 Vibe 구매 테이블과 Stella 구매 테이블은 공유하지 않는다. 계정 identity만
중앙 Sobok OIDC issuer를 공통으로 사용한다.

### 한국 결제 확정 방향

- PortOne V2와 기존 대표 Store를 사용한다.
- production은 토스페이와 신용·체크카드 중 하나를 사용자가 고르게 한다.
- 서버는 토스페이를 `tosspay_v2`·`EASY_PAY`, 카드를 `tosspayments`·`CARD`로 매핑한다.
- 토스페이는 실연동, 토스페이먼츠는 카드사 심사 동안 테스트 채널을 사용한다. 승인 뒤 중앙
  카탈로그의 카드 channel key와 `mode`만 실연동으로 교체한다.
- Store ID와 channel key는 브라우저 결제 요청에 포함되는 공개 식별값이다.
- PortOne API Secret과 대표 Store의 공용 test/live Webhook Secret은 중앙 payments Worker의
  Secrets Store binding 밖으로 노출하지 않는다. Stella Worker에는 PortOne 자격증명을 두지 않으며
  PG의 서버 API·secret key는 PortOne 콘솔에만 둔다.
- 중앙 channel entry는 `channelKey`·`mode`·제품 `scopes`를 함께 가지며 Stella RPC는 `stella`
  scope가 있는 채널만 반환한다.
- 두 배포는 환경별 Supabase project와 Database Worker의 공용 fresh Hyperdrive를 사용한다.

### test/live 데이터 경계 확정안

같은 테이블에 `environment` 컬럼을 반복하고 모든 조회에 필터를 추가하지 않는다. production과
staging을 별도 Supabase Pro 프로젝트로 나누고 두 프로젝트 모두 고정 `stella` schema를 쓴다.

- 공개 Worker는 환경별 Database Worker만 바인딩하고, Database Worker가 `sobok_runtime`과 fresh Hyperdrive를 바인딩한다.
- Drizzle table은 `pgSchema('stella')`로 schema를 항상 SQL에 명시한다. 환경별 schema 상수나
  production fallback은 없다.
- `sobok_runtime`의 `search_path`는 `pg_catalog`만 두어 비한정 테이블명이 우연히 해석되지 않게 한다.
- staging은 `staging` 브랜치 push가 시작한 통합 워크플로가
  staging의 `SOBOK_MIGRATOR_URL`로 `drizzle-kit push`한 뒤 Worker를 배포한다. 명확한 비파괴 변경은
  자동 적용하고 data loss나 rename hint가 필요한 변경은 배포를 멈춘다. production은 `main`의 수동
  schema workflow에서 explain 결과를 검토한 뒤 별도 apply로 반영한다.
- Worker와 정적 자산은 로컬 `wrangler deploy`로 배포하지 않는다. staging은 `staging`, production은
  `main` 브랜치의 수동 전체 배포 workflow만 사용한다.
- 중앙 payments의 channel entry에 test/live mode와 제품 scope를 고정하고 브라우저가 channel key나
  mode를 선택하지 못하게 한다. production에서 시작한 테스트 결제 웹훅도 테스트 URL로 들어오므로
  심사 거래는 브라우저 confirm과 production 재조정으로 완료한다. 제품 Worker는 PortOne 자격증명을
  갖지 않는다.

이 방식은 테스트 구매와 실제 컬렉션, 자격증명, 연결 풀, 장애 범위를 프로젝트 경계로 분리한다.
행마다 환경을 검사하거나 schema를 동적으로 선택하는 방어 로직은 필요 없다.

공식 연동 기준:
[PortOne V2 토스페이](https://developers.portone.io/opi/ko/integration/pg/v2/tosspay-v2?v=v2),
[PortOne V2 인증 결제](https://developers.portone.io/opi/ko/integration/start/v2/checkout)

### 중국 본토 확정 방향

중국 본토 결제 제공자는 PortOne의 이지페이(KICC) 해외결제로 확정했다. 신규 연동은 PortOne이
권장하는 V2를 사용하는 현재 권장안이다.

PortOne 공식 문서상 현재 KICC 해외결제는 다음 범위를 지원한다.

- 인증 결제창 방식
- 위챗페이
- 알리페이 플러스와 Alipay 월렛
- 결제 통화 `KRW`, `USD`
- 결제창 로케일 `ZH_CN`

구현 시 지켜야 할 사항은 다음과 같다.

- 위챗페이와 일부 알리페이 플러스 결제는 QR 스캔 뒤 결제창이 닫혀도 나중에 승인될 수 있으므로
  웹훅과 서버 조회를 기준으로 처리한다.
- 위챗페이 취소는 비동기이므로 취소 API 응답만으로 `cancelled`로 바꾸지 않고 웹훅 결과를 기다린다.
- 위챗페이 모바일 결제를 열 도메인은 KICC에 미리 등록한다.
- 위챗페이 테스트 MID는 PC 결제만 지원하므로 모바일 흐름은 운영 MID를 사용한 별도 검증이 필요하다.
- KICC의 주문명과 알리페이 플러스 주문 설명에는 영문 사용을 기본으로 한다.

공식 연동 기준:
[PortOne V2 이지페이(KICC) 해외결제](https://developers.portone.io/opi/ko/integration/pg/v2/kicc-v2?v=v2),
[PortOne PG 지원 범위](https://developers.portone.io/opi/ko/integration/pg/v2/readme)

중국 사용자에게 표시할 기준 가격과 실제 청구 통화를 KRW 또는 USD 중 무엇으로 할지는 아직
결정하지 않았다. 중국 로케일 가격은 한국 원화 가격을 단순 환산하지 않고 현지 결제 전환을 따로
측정한다.

한국과 중국은 같은 카드 카탈로그와 Sobok 계정을 사용할 수 있지만 결제 채널, 가격표, 로그인 제공자,
전달 채널은 로케일별 설정으로 분리한다. 중국 본토용 별도 배포가 필요한지는 결제와 별개의 인프라
결정으로 남긴다.

## 11. 서버 구현 기준

2026-08-03 기준 유료 MVP의 서버 권위 데이터와 production 확장 기반은 다음과 같이 구현한다.

- `CURRENT_GUARDIAN_MANIFEST`는 현재 판매하는 4개 패밀리·7개 에디션, SKU별 시장 가격표,
  희귀도 가중치와 보장 규칙을 담은 단일 정본이다. production 출시에는 같은 계약으로 최소
  1,024개 에디션을 게시한다. 수동 manifest pointer나 버전 registry는 두지 않는다.
- 구매 행에는 실제 상품명·가격·통화·지급 entitlement를 저장하고, 완료된 리포트와 카드 획득에는
  렌더된 결과와 실제 추첨 후보·가중치·보장 적용을 저장한다. 과거 결과를 현재 카탈로그로 재계산하지
  않는다.
- family와 edition ID는 현재 매니페스트의 literal union으로 제한하지 않는다. 이후 게시되는
  패밀리와 에디션도 같은 문자열 ID 계약과 스냅샷 형식을 사용한다.
- 모든 family와 edition은 각각 하나의 공통 pool에 속한다. `single`, `context_scored`,
  `weighted_random` 선택 정책을 같은 resolver가 처리하며, 사랑과 나머지 슬롯을 위한 별도
  에디션 자료구조나 고정 카드 전용 함수는 두지 않는다.
- 무료 질문은 정적 registry에 두고, 유료 질문 원문·선택지·적응형 선택 정책·점수는 Git JSON을 source of
  truth로 삼아 Database Worker 서버 번들로 배포한다. paid session은 다음 질문만 전달하며 최종
  report에는 차트, discriminated answer map과 합산 signal map을 스냅샷으로 저장한다. 구체적인
  원본 계약과 배포 절차는 [유료 질문 콘텐츠 계약과 배포](./paid-questionnaire-content.md)를 따른다.
- 희귀도는 서버 Web Crypto로 추첨하며 10,000 정수 가중치를 사용한다. 나머지 연산 편향이 없도록
  rejection sampling으로 난수를 가중치 구간에 매핑한다.
- `guardian_collection`을 게스트와 계정이 공유하는 소유권 집합으로 사용한다. 계정 생성 시 이 집합을
  연결하고 카드나 보장 카운터를 복사하지 않는다.
- 리포트 입력·선택 패밀리·최초 네 카드·렌더된 본문을 `guardian_report`에 스냅샷으로 보존한다.
- 완료된 한국어 hero·네 섹션·종합 문장도 `narrative_snapshot`에 렌더된 문자열로 보존한다. GET은
  현재 copy로 다시 계산하지 않으며 상세 계약은
  [한국어 개인화 리포트 본문 엔진과 최종 계약](./paid-report-content-engine.md)을 따른다.
- 모든 획득은 `guardian_card_acquisition`에 추가하고, 빠른 조회용 보유 집계는
  `guardian_card_ownership`에 트랜잭션으로 함께 반영한다.
- 카드 획득 시 locale별 이름·대체 텍스트·한 줄과 원화 경로를 `presentation_snapshot`으로 고정한다.
  이후 카탈로그나 문구를 개정해도 이미 공개한 카드 표현은 조용히 바뀌지 않는다.
- 같은 획득 행의 `draw_snapshot`에는 family·edition 후보, 선택 방식, 가중치 합, 실제 eligible 후보,
  보장 간격과 적용 여부를 고정한다.
- `guardian_report_card_selection`은 슬롯별로 현재 걸어 둔 acquisition을 가리킨다. 최초 fulfillment가
  네 슬롯을 채우고 재추첨은 이 포인터를 자동 변경하지 않으며, 명시적 선택 API만 사랑 슬롯을 바꾼다.
- 재추첨권은 출처 없는 잔액 대신 `guardian_redraw_grant`로 기록한다. 결제와 계정 저장 보상을
  별도 grant로 구분하고 각각 한 번만 발급한다.
- 유료권 차감, 미보유 판단, 추첨, 획득 이력, 보유 집계, 보장 카운터 변경을 한 DB 트랜잭션으로 묶는다.
- 재추첨 checkout UUID는 같은 PortOne 주문을, draw UUID는 같은 acquisition을 반환한다. 네트워크 재시도나
  더블 클릭이 새 주문을 만들거나 크레딧을 두 번 차감하지 않는다.
- 공용 scheduler는 이미 지급된 크레딧·카드·결제 이력은 유지하고, 크레딧을 지급하지 않은 채 30일 지난
  재추첨 pending·failed·cancelled 주문만 정리한다.
- 결제 확인 반환, 웹훅, 재조정 작업은 같은 멱등 구매 확정 함수를 호출하며 전체 리포트 결제
  확정은 카드가 아니라 질문 entitlement만 지급한다.
- 전체 리포트 entitlement와 durable 복구 메일 intent를 같은 구매 트랜잭션에서 만들고 실제 Resend
  호출은 커밋 뒤 실행한다. 결제 완료 메일과 구매 이메일 재발급은 15분·1회용 token만 전달하고,
  교환 성공 시 collection capability를 교체한다. 장기 capability 원문은 메일이나 URL에 넣지 않는다.
- 마지막 유효 답변 저장, answer·signal snapshot, 패밀리 선택, 사랑 희귀도 추첨, 최초 네 장
  획득 이력과 `fulfilled` 전환은 하나의 report 트랜잭션으로 묶는다.
- capability 보호 API는 상품·확률·보장 메타데이터와 guest checkout, 결제 확인, 유료 질문 진행, 최종
  report 조회에 더해 사랑 재추첨 상태·checkout·draw·대표 카드 선택을 제공한다. 계정 귀속 mutation은
  Stella의 Sobok OIDC session과 `(issuer, sub)` 소유권 경계를 사용한다.
- production과 staging은 환경별 fresh Hyperdrive와 각 프로젝트의 `sobok_runtime` role을 사용한다.
  schema는 둘 다 코드에 고정한 `stella`이며 Hyperdrive 캐시는 read-after-write 일관성을 위해 계속 끈다.

DB 스키마는 코드에 선언하고 staging은 통합 배포의 선행 단계, production은 명시적 운영 단계에서
`drizzle-kit push`한다. 질문 콘텐츠 테이블은 두지 않고 답변 행에는 안정적인 문자열 question·option ID만
저장한다. 질문 원문과 선택 정책 변경은 DB 게시나 해시 검증 없이 검증된 Database Worker 번들 배포로
반영한다.

한국 전체 리포트의 guest draft, checkout, confirm, webhook, report read API와 화면 상태의 구체적인
계약은 [한국 전체 리포트 결제·공개 수직 슬라이스](./korea-paid-report-vertical-slice.md)에 고정한다.

## 12. 확정·권장·미정 요약

### 확정

- 웹 중심 서비스
- 한국 → 중국 본토 → 이후 미정 순서
- `accounts.sobok.cc` Sobok 통합 계정과 Stella host-only OIDC session
- 계정 보관을 선택하면 출생일·시간·장소 서버 저장 가능
- 첫 구매는 네 주제 전체 리포트
- 유료 MVP는 4개 패밀리·7개 실제 에디션, production 출시는 실제 3:4 에디션 최소 1,024장
- 유료 MVP 답변은 네 주제 상세 본문·해석 초점·한 줄을 실질적으로 바꿈
- production에서는 출생 차트와 질문에 따라 네 기본 카드 패밀리와 원화가 달라짐
- 무료 미리보기는 질문 2개, 유료 개인화 질문은 서버 결제 확인 뒤 제공
- 유료 질문은 핵심 12개, 주제별 필수 맞춤 4개, 필요 시 심화 최대 4개로 전체 16~20개
- 자유 입력은 필수 0개, 선택 사항으로 최대 1개
- 사랑만 네 단계 희귀도를 무작위 추첨
- 이후 사랑 카드만 저가 재추첨
- 재추첨은 일러스트와 한 줄만 변경
- 게스트 이메일은 결제 직전 필수 복구 채널이며 계정 생성과 분리
- 중복 허용과 일정 횟수마다 미보유 보장
- 기본 카드에 희귀도·계절·의상 변형을 더해 장기적으로 수천 장
- 중국 본토 결제는 PortOne 이지페이(KICC) 해외결제
- Orbit 55%, Nebula 30%, Eclipse 12%, Stella 3%
- 유료 다섯 번째 재추첨마다 미보유 에디션 보장
- 전체 리포트 3,900원
- 사랑 카드 재추첨 1회 700원
- 사랑 카드 재추첨 5회 2,500원
- 계정 보관 보상으로 첫 미보유 재추첨 1회
- `stella-stg`와 `stella` 배포 분리
- Supabase project·Database Worker·fresh/cached Hyperdrive를 production/staging으로 분리
- 두 프로젝트 모두 코드에 고정한 `stella` PostgreSQL schema 사용
