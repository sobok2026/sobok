# 카페 제조 자료 운영

사용자는 제공한 원부재료·레시피 자료를 공개 소스와 빌드에 사용하는 것을 허용했다. `apps/cafe/data/` JSON을 Git으로 관리하고 월간 갱신 때 직접 수정한다. 현재 형식만 사용하는 정책은 [아키텍처](./architecture.md#저장과-탭-정책)를 따른다.

## 자료 범위

아카데미 영상 표, 제공된 5lb 콜드 브루 배합, 부재료 제조표를 수록한다. [자료 범위](../../apps/cafe/data/coverage.json)에 표 미검출 영상과 미변환 전자책을 남기며 전체 목록을 변환했다고 표시하지 않는다. 원본 영상·이미지는 앱이나 빌드에 포함하지 않는다. `references/`의 엑셀은 참고 자료이며 가져오기 파이프라인으로 사용하지 않는다.

2026-09-29 사용자 결정으로 아카데미 자료에 빠진 제조법·규격은 사용자가 제공한 Quizlet 공개 보조 자료로 보완한다. 아카데미와 충돌하면 아카데미를 우선한다. 보조 자료의 출처와 적용 범위를 레시피 메모와 [대조 기록](./preparation-source-comparison.md#공개-보조-자료-보완--2026-09-29)에 남기며, 원문에 없는 작업·수율은 사용자 확인을 받아 게임 운영값과 구분한다.

판매에는 공개 가격·원문 계량·제공 용기·부재료의 전체 준비 경로가 갖춰져야 한다. 원문 검토, 미기재 수량, 게임의 장비 지원 여부는 구분한다. 자료실은 판매 여부와 관계없이 원문을 보여준다. 현재 판매·준비 가능 범위는 `check:recipes` 결과로 확인한다.

## 자료의 경계

- `data/recipes/`와 재료·장비·용기·품질 자료에는 확인된 제조 사실을 둔다.
- `data/menu.json`에는 확인한 판매 가격을 둔다.
- `data/shop/`에는 사용자가 승인한 게임 재고·환산값·제공 용기·커스텀 운영값을 둔다. 원문의 빈칸을 이 값으로 채우지 않는다.
- 음료와 부재료는 같은 제조 실행을 사용한다. 한국어 이름·설명문·엑셀 행 번호로 행동을 추정하거나 음료별 별도 엔진을 만들지 않는다.

판매 가격의 공개 출처와 적용 범위는 [가격 근거](./menu-prices.md)에 둔다. 앱에는 사이즈별 가격 한 개만 저장한다. 과거 메뉴판으로만 확인된 가격을 현재 매장 가격이라고 단정하지 않으며, 다른 사이즈의 차액으로 가격을 만들어내지 않는다. `single`은 솔로·도피오·칵테일 등 고정 제공 규격이며 임의로 Tall이나 특정 ml로 바꾸지 않는다.

## 제조 데이터 작성 원칙

- 재료·레시피·제조 구분·단계·장비·장비 프로그램·용기·POS 메뉴 그룹의 고정 ID는 영문 소문자·숫자를 하이픈으로 연결한 `kebab-case`로 작성한다. 장비 프로그램 번호처럼 숫자만 있는 ID도 허용한다.
- 레시피 파일명은 문서 ID와 같게 둔다. 메뉴의 `recipeId:variantId`, 준비 산출량의 `recipeId/variantId`는 각 ID를 기존 구분자로 연결한다. 이름이 바뀌어도 ID는 유지하며 `name`·`label`·설명·원문 조건은 한글로 보존한다. 상태 필드·코드 변수의 `camelCase`와 실행 중 생성하는 UUID는 별도다.
- ID 변경은 정의·참조·재고 키·POS 연결을 함께 수정한다. 이전 ID의 별칭·변환표·저장 버전·마이그레이션은 두지 않는다. 기존 ID가 남은 게임 저장·JSON 백업은 현재 형식으로 읽지 못할 수 있으며 새 근무를 시작한다.
- 별도 등록된 재료는 영어 이름이 비슷해도 합치지 않는다. `green-tea-bag-for-base`와 `green-tea-bag-for-iced-tea`, `mango-passion-fruit-juice`와 `mango-passion-fruit-juice-for-banana`는 각각 유지한다.
- `amount`는 투입량, `count`는 펌프·샷·스쿱 등의 횟수다. `line`, `mark`, `fill-volume`, `rim-gap`은 내용물이 도달할 기준이다. 투입량과 최종 도달선을 바꾸지 않는다.
- 사이즈별 수량은 `by-size`로 기록한다. 다른 사이즈의 눈금·스쿱은 `referenceSize`로 지정한다.
- 컵 기준선과 텀블러 ml 계량은 서로 다른 조건이다. 텀블러 수량을 컵 선의 실측 용량으로 쓰지 않는다.
- 펌프 횟수와 토출량을 구분한다. 10.2ml × 18펌프는 183.6ml이며 원문의 180ml는 사용자가 확인한 반올림 표기다.
- `run-machine.program`은 프로그램 번호, `cycles`는 작동 횟수다. 3번 프로그램 1회는 블렌딩 3회가 아니다.
- 범위·대략값·최소 횟수를 보존한다. 소수 횟수는 해당 분할 단위로 조작한다. 빈칸을 0이나 임의의 기본값으로 채우지 않는다.
- 계량 기준이 없으면 `unspecified`, 완성 수율이 없으면 `output.amount: null`로 둔다. 판매를 위해 원문 데이터를 추정치로 채우지 않는다.
- 대체 계량법은 `alternatives`, 조건은 `when`, 원문에 명시된 기본 커스텀은 `defaults`로 관리한다. 한국어 이름을 검색해 기본 선택을 추측하지 않는다.
- 물성이 묽을 때 추가 블렌딩하는 등의 관찰 조건은 제조 중 확인한다. 같은 원문 단계에 속한 동작은 같은 조건 결정을 공유한다.
- 단계의 `label`은 원문 단계 이름이다. JSON에 화면용 동작별 이름을 따로 적지 않는다.

원문에 없는 재혼합 횟수, 얼음 스쿱 수, 혼합·에스프레소·스팀 시간을 만들지 않는다. 게임용 스팀 시간은 [임시 규칙](./prototype-rules.md#임시-수치와-단순화)으로 구분한다. 원문의 프로그램 시간, 공기 주입, 티백 물기 빼기, 콜드 브루 20시간은 유지한다. 게임 시계를 가속해도 제조 기간 자체는 바꾸지 않는다.

## 게임용 운영값과 컵 용량

사용자가 승인한 게임용 원팩·입고가·초기 재고·기한·환산값·준비 산출량은 `data/shop/`에 둔다. 원문에 명시된 단위와 토출량, `lineVolumes`의 ml를 우선하며 불명확한 재고 환산만 운영값을 사용한다. 이 값은 제조 목표나 자료실의 원문을 바꾸지 않는다.

한국 매장용 샷당 원두량은 공개 자료에서 확정하지 못했다. [Starbucks at Home](https://www.starbucksathome.com/brewing-guide/how-use-espresso-machine-brew-espresso)의 가정용 안내를 매장 머신 규격으로 단정하지 않는다. 재고용 9g/샷은 게임 설정이다.

`cold-brew-batch`는 제공 자료의 5lb·물 14L·20시간이며 완성량 3L는 게임 재고량이다. 별도 `cold-brew-toddy`의 3lb·물 5L 후 4L·20시간·완성 원액 6L를 다른 배합에 대입하지 않는다.

## 제공 용기와 컵

컵 종류·규격의 근거는 [매장·포장 컵](./design.md#매장포장-컵)에 둔다.

2026-09-27 사용자 결정으로 원문에 없는 제공 용기를 게임 설정으로 정했다. 칵테일은 원문이 `전용 잔`으로만 적으며 모두 매장에서만 판매한다.

- 마티니·시트러스 콜드브루 마티니·에스프레소 마티니·라떼 위스키 마티니는 `martini-glass`, 딸기 레몬 보드카 블렌디드는 `tulip-glass`다. 장충라운지R점 사진([신세계그룹 뉴스룸](https://www.shinsegaegroupnewsroom.com/go-hyeongjang-estate-starbucks-lounge/), [덴 매거진](https://www.theden.co.kr/news/articleView.html?idxno=2958), [아주경제](https://www.ajunews.com/view/20240911202804145))에서 잔 모양을 확인했다.
- 사진으로 확인하지 못한 아페롤 스프릿츠·오미자 유스베리 모히토와 기존 `cocktail-glass` 음료는 `cocktail-glass`로 두고 하이볼 모양으로 그린다.
- 스타벅스 더블 샷 원문은 7oz 컵과 전용 리드만 적는다. 포장은 `double-shot-cup`, 매장은 `double-shot-glass`로 나누고 리드는 포장에만 덮는다.

## 월간 갱신

1. 바뀐 원문을 대조해 제조 구분·수량·순서·조건을 해당 JSON에서 수정한다.
2. 필요한 재료·장비·용기를 연결한다. 미확인 수량은 미확인 상태로 남긴다.
3. 판매할 규격의 공개 가격을 `menu.json`에 넣고 근거 문서를 갱신한다. 새 재료의 게임 재고 설정도 `data/shop/`에 추가한다.
4. 원문 확인이 끝난 `review`를 해소한다. 새 추출 자료를 확보했으면 `coverage.json`도 갱신한다.
5. 검사 결과의 제외 사유를 확인하고 영향을 받는 주문·제조·준비·판매 화면을 확인한다.

```sh
bun run --filter=@sobok/cafe check:recipes
bun run --filter=@sobok/cafe type
bun run --filter=@sobok/cafe build
```

`check:recipes --details`는 메뉴별 판매 보류 사유를 출력한다. `dev`와 `build`도 자료 검사를 먼저 실행한다. 새 행동 종류가 없으면 음료별 실행 코드나 POS 분기를 추가하지 않는다.
