# 카페 게임 구현 준비

현재 구현 이후의 우선순위·범위·완료 기준은 [후속 작업 분석](./next-steps.md)을 따른다. 아래 구현 순서는 기반 작업의 순서와 완료 기록이다.

## 착수 조건

게임의 목적, 핵심 업무, 초기 메뉴와 시간 흐름은 정해졌다. 실제 계량 용기의 형상, 일부 장비 시간, 세척 세부와 날짜 계산 관례는 추가 확인이 필요하다.

사용자에게 확인한 착수 결정:

- 기존 프로젝트 구조에 얽매이지 않고 구현에 맞는 방식을 선택한다. `apps/cafe`에 Vite + React + TypeScript + Three.js를 사용한다.
- 제공한 자료를 공개해도 된다. 원본 배합·품질 기준을 변환한 데이터를 소스와 빌드에 포함한다.
- 미확인 절차는 게임용 임시 규칙임을 문서에 표시하고 첫 플레이 버전을 구현한다.

## 저장소에서 확인한 기본값

- Bun workspaces의 `apps/*`에 독립 앱을 둔다.
- 기존 게임 앱은 `@sobok/next-config`의 정적 내보내기를 사용하지만 이 앱은 사용자 허용에 따라 Vite의 브라우저 전용 정적 빌드를 사용한다.
- React는 POS·운영 UI, Three.js는 매장·시점·상호작용을 담당한다. 프레임별 카메라 처리는 React 렌더와 분리한다.
- React UI는 Tailwind CSS v4와 공식 Vite 플러그인으로 스타일링한다.
- 원격 데이터베이스, API route, Server Action은 이 게임에 필요하지 않다.
- Cloudflare 원격 변경은 별도 배포 단계다. 이 작업에서는 로컬 구현과 빌드 확인을 진행한다.
- 로직은 먼저 앱 안의 호출부 근처에 두고, 다른 앱과 실제로 재사용할 때 공용 패키지를 검토한다.

## UI 스타일

- `apps/cafe/vite.config.ts`에서 `@tailwindcss/vite`를 연결한다. `src/style.css`의 `source('.')`는 클래스 탐색 기준을 이 앱의 소스 디렉터리로 고정한다.
- 색상·글꼴·반복되는 글자 크기·그림자·화면 너비 기준은 `@theme`으로 정의한다. 낮은 화면의 HUD 배치는 `short`·`compact` 높이 변형을 사용한다.
- 각 JSX 요소에 유틸리티 클래스를 작성한다. 기존 화면 클래스나 `@apply` 기반 컴포넌트 스타일은 두지 않는다. Three.js가 생성하는 canvas는 호스트의 하위 요소 변형으로 크기를 지정한다.
- 반복되는 일반 버튼은 `Button.tsx`, 작업 HUD·제목·조작 버튼·게이지는 `WorkControls.tsx`에서 공유한다. 버튼의 색상과 크기는 명시적인 variant·size로 선택하고, 호출부의 `className`은 배치용으로 사용한다.
- 클래스 이름의 일부를 동적으로 이어 붙이지 않는다. 상태는 완전한 클래스 문자열 또는 `data-*`·이름 있는 `group` 변형으로 표현한다. 재고 펼침 상태는 네이티브 `details`의 `open`을 따른다.
- 실행 중 계산되는 게이지 너비·목표 위치는 인라인 스타일로 전달한다. 정적인 배치와 장식은 Tailwind로 관리한다.
- Preflight의 초기화를 기준으로 여백·목록·타이포그래피를 요소에 명시한다. 전역 CSS에는 테마와 기본 요소 규칙만 두며, 키보드 `focus-visible`과 동작 줄이기 설정을 반영한다.

참고: [Vite 설치](https://tailwindcss.com/docs/installation/using-vite), [테마 변수](https://tailwindcss.com/docs/theme), [클래스 탐색](https://tailwindcss.com/docs/detecting-classes-in-source-files), [유틸리티·반복 스타일·인라인 값](https://tailwindcss.com/docs/styling-with-utility-classes), [Preflight](https://tailwindcss.com/docs/preflight), [상태 변형](https://tailwindcss.com/docs/hover-focus-and-other-states), [W3C 키보드 포커스 표시](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html).

## 구현 순서

### 1. 공간과 입력

매장, 작업대, 물체, 첫 시점, 이동·충돌·시선 상호작용을 만든다. 시작·일시정지와 작업 안내를 연결한다. 메뉴 UI와 게임 입력이 동시에 동작하지 않도록 한다.

### 2. 주문에서 전달까지

손님 요청과 POS 입력을 별도로 저장한다. 컵 준비, 단계별 제조, 재료 소비, 완성 판정, 전달, 재제조를 연결한다. 임시 규칙은 설정에 모으고 실제 기준과 구분한다.

### 3. 지원 업무

사용한 도구가 세척 대상으로 이어지고, 세척한 도구를 제자리로 돌려놓게 한다. 테이블 상태, 재고 보충, 용기별 잔량·라벨 확인을 연결한다. 지원 업무 없이 제조만 무한 반복할 수 없게 한다.

### 4. 시간과 근무 마감

게임 시계, 신규 주문 마감, 남은 주문 처리, 정리, 결산, 다음 날을 연결한다. 기한과 장시간 준비 작업은 같은 게임 시계를 기준으로 한다. 일시정지와 백그라운드 상태에서는 진행하지 않는다.

### 5. 저장과 복구

IndexedDB에 현재 상태를 저장한다. 입력 검증, 저장 실패 안내, 이전 정상 저장, 파일 백업·복원을 제공한다. 저장 버전 관리와 이전 구조의 마이그레이션은 사용자 요청에 따라 구현하지 않는다. 탭 간 상태 동기화는 구현하지 않고 현재의 Web Locks 중복 실행 제한을 유지한다. 자동 잠금 인계나 잠금 획득 시점 변경도 추가하지 않는다. 저장 완료 전 페이지를 닫는 경우는 필요한 브라우저 확인 항목으로 둔다.

## 완료 기준

브라우저에서 들어가 이동하고, 주문 한 건을 접수·제조·전달할 수 있다. 그 과정에서 재료와 도구 상태가 바뀌고 청소·설거지·정리·보충으로 회복된다. 근무를 마감하고 다음 날 또는 저장한 상태로 이어진다.

소스의 타입 검사와 빌드, 실제 브라우저 플레이로 동작을 확인한다. 테스트 코드 작성은 이번 범위에 포함하지 않는다.

## 추후 확정할 실제 절차

컵·피처의 계량선 형상, 샷 이관, 원팩의 포장 규격, 배합 용기와 혼합 시간, 스팀 모드, 세척·건조 순서, 기한 계산 관례, 장시간 추출의 후속 처리다. 첫 플레이 버전의 단순화는 [구현 규칙](./prototype-rules.md)에 기록한다.

## 직접 제조 구현 확인

2026-09-24 기준으로 준비된 주문·재료 상태에서 브라우저의 이동·집기·붓기·펌핑 조작을 사용해 콜드 브루, HOT·ICED 블랙 글레이즈드 라떼의 제조와 전달을 확인했다. 판매액·재고 소비·피처 상태가 반영되고, 네 번째 소스 펌핑은 오류로 기록되며 폐기해도 사용한 재료는 반환되지 않는다.

계량 도중 저장 후 새로고침, 진행 중 작업의 완료, 창 포커스 이탈 시 투입 정지, 제조 HUD의 마우스 누름·해제를 확인했다. 타입 검사와 Vite 빌드를 통과했고 자동 테스트 파일은 추가하지 않았다. Three.js 장면 청크에는 Vite 기본 500kB 크기 경고가 남아 있다.

직원 동선은 카운터 안쪽으로 수정했다. 장비 전면·컵·추출 위치와 POS가 직원 쪽을 향하고, 픽업대·세척대·도구 선반도 같은 업무 공간에 연결된다. 직원 통로에서 콜드 브루 주문 접수부터 제조·전달까지, 샷 추출과 세척·정리, 고객 쪽 제조 차단과 카운터 충돌을 브라우저에서 확인했다. 새 근무는 직원 통로에서 시작하고 저장한 근무는 저장 위치에서 이어진다.

부재료 준비는 폼·바모카의 직접 계량·혼합·라벨·보관까지 연결했다. 브라우저에서 폼 7펌프와 25초 블렌딩, 바모카 원팩·온수·젓기, 준비 도중 저장 복원, 잘못된 보관 위치 안내와 올바른 보관 후 재고 반영을 확인했다. 원팩은 개봉·라벨 단계에서 사용 가능량이 늘지 않고 보관 완료 후 증가한다. 사용한 피처는 세척 대상으로 돌아가며, 과다 계량 폐기와 만료 배치 차단도 확인했다.

피처 세척은 문지르기·헹구기·집기·운반·선반 정리로 연결했다. 세척 중 손을 떼면 멈추고 저장 후 같은 진행량으로 이어진다. 세척 중인 피처, 세척 완료 대기 피처와 들고 있는 피처를 구분해 중복 회수하지 않는다. 다른 작업대에 컵을 두면 혼합 작업대의 청소 메뉴에 접근할 수 있고, 빈손이 필요한 업무에는 컵을 내려놓으라는 안내를 표시한다. 재접속 시 저장된 카메라 방향도 유지한다.

작업대에 컵·부재료·세척 작업이 남으면 마우스 시점 복귀까지 막던 조건을 제거했다. 근무 시작·재개, WASD 이동, 컵·피처 집기, 작업 종료 시 마우스 고정을 요청하고, 제조·준비·세척 버튼을 사용하는 동안에는 커서를 해제한다. 작업 시작 시 고정 요청과 해제 요청이 겹치지 않도록 분리했으며 입력 모드를 하단에 표시한다. 브라우저에서 진행 중인 작업을 복원한 뒤 재개·이동·컵 집기·세척 취소의 고정 요청과 작업 시작 시 커서 유지, 기존 작업 상태 보존을 확인했다. 검증용 macOS Chrome은 네이티브 포커스 제한으로 `requestPointerLock`을 거절해 실제 고정 후 마우스 이동은 확인하지 못했으며, 이 환경에서는 대체 조작 안내가 표시됐다. 타입 검사와 빌드는 통과했다.

최신 초기 상태에서 브라우저 키보드·화면 버튼으로 콜드 브루 → HOT 라떼 → ICED 라떼 → 마감 → 다음 날을 완주했다. 추가 재료나 도구를 미리 넣지 않고 초기 원팩 개봉·라벨·보관과 폼·바모카 직접 준비를 수행했다. HOT 소스 과다 펌핑으로 컵 한 개를 폐기한 뒤 재제조했다. 결과는 전달 3잔, 매출 18,000원, 청소 6회, 세척 5회, 재제조 컵 1개였다. 마감 시 피처는 깨끗함 3개·오염 0개·세척 완료 대기 0개이고 세척/운반 작업이 남지 않았다.

20시간 콜드 브루 추출을 시작하고 마감한 뒤 다음 날 3,000ml 배치가 생성되는 것을 확인했다. 다음 날 만료된 휘핑크림은 사용 가능량 0으로 표시됐고 폐기할 수 있었다. 후방 컵 24개에서 6개를 보충해 다음 근무를 준비했다. 이 확인용 근무의 잔액은 매출과 추출 준비비 9,000원을 반영한 59,000원이었다.

첫 구현은 로컬 빌드까지 진행했다. 운영 배포는 Vite가 생성하는 `dist`를 Cloudflare Workers Static Assets로
제공한다. GitHub Actions의 `Cafe Deploy` 또는 `Production Deploy`가 Worker를 배포하고,
`sobok-ops`의 `account-workers` HCP Terraform workspace가 `cafe.sobok.cc` custom domain을 소유한다.
스테이징은 구성하지 않는다.

## HUD 정보 위계 정리

주문은 왼쪽 위에 메뉴·온도·상태로 요약하고, 손님 요청과 주문표가 다를 때만 입력한 메뉴와 수정 안내를 펼친다. 이동 안내와 직접 제조·준비·세척 조작은 하단 중앙의 한 영역을 사용한다. 현재 단계의 목표량과 가능한 조작을 표시하고, 도구 집기 → 사용 → 도구 놓기 → 확인에 따라 강조가 이동한다. 계량 도중 강조가 바뀌어도 누르기 입력은 유지한다. 부족한 재료와 피처는 해당 작업 안에서 안내한다.

운영 수치와 정리 목록은 M으로 여는 매장 현황에 모았으며 확인 중에는 일시정지한다. 정상 저장 안내와 전체 단축키는 일시정지 메뉴로 옮겼다. 결과 알림은 3초, 오류는 6초 후 사라지고 사용자가 직접 닫을 수도 있다. POS의 영업 관리, 레시피·작업 안내, 재료별 배치 상세는 접어두고 필요할 때 펼친다. 재고는 기한·라벨·보관 확인이 필요한 배치와 사용 가능량이 없는 재료부터 보여준다.

1280×720에서 첫 콜드 브루의 접수·키보드/마우스 계량·도구 조작·전달, 피처 문지르기·헹구기·운반·선반 정리, 원팩 개봉·라벨·보관, 폼 직접 준비·블렌딩·라벨·보관을 확인했다. 실제 초기 재고에서 진행했으며 전달 1잔·매출 5,000원·피처 세척 1회와 폼 450ml 보관 결과를 확인했다. 매장 현황의 키보드 열기·닫기와 포커스 순환, 잘못된 보관 위치 안내도 확인했다.

## 직접 청소와 운영 기록 확인

테이블·작업대의 자동 타이머를 직접 조작으로 바꾸고, 두 테이블의 컵·얼룩을 분리했다. 브라우저에서 컵을 든 채 저장·새로고침한 뒤 분리수거함에 옮기고, 닦기 진행 42%를 저장·복원해 완료했다. 두 번째 테이블을 정리해도 첫 번째 테이블의 컵·얼룩은 유지됐으며, 작업대·분리수거와 기존 피처 세척·선반 정리를 함께 진행했다.

청소·결산 연결을 확인한 근무에서는 콜드 브루 과다 계량 후 컵을 폐기해 실제 소비량 97.6ml가 폐기로 기록됐다. 다시 만들어 전달한 판매액 5,000원과 우유·컵·콜드 브루 준비비 14,000원을 반영해 잔액은 41,000원이었다. 개봉 후 폐기한 휘핑크림 1,000ml도 별도 기록됐다. 정리를 끝내고 결산·다음 날까지 진행하니 시작 잔액 41,000원으로 당일 기록이 초기화되고, 추출 완료한 콜드 브루 3,000ml와 만료된 초기 휘핑크림이 재고에 반영됐다.

## 컨디먼트 바와 소모품 확인

사용자 추가 요청으로 두 테이블 사이 창가에 컨디먼트 바를 배치했다. 컵 반납 90%·테이블 방치 10%, 사용한 테이블·반납대·작업대의 오염 30%를 적용한다. 확률은 전달 성공 시 한 번 계산해 게임 상태에 저장한다. 얼룩 없이 컵만 있는 자리는 회수·분리수거만으로 청소를 마친다. 손님이 걸어서 이동·착석·반납·퇴장하는 동작은 CAFE-04에서 연결했다.

추가 후 초기 상태에서 콜드 브루를 제조·전달하니 컵이 테이블에 남고 얼룩은 생기지 않는 경우가 나왔다. 냅킨·빨대는 각각 진열 20개에서 19개로 줄었다. 냅킨 100장 입고비 1,000원은 지출에 기록됐고, 1장을 집은 뒤 진열 19장·후방 199장·운반 1장 상태를 저장·복원했다. 창고에 다시 놓으면 후방 200장으로 돌아갔고, 다시 집어 실제 이동 후 컨디먼트 바에 놓으니 진열 20장·후방 199장·운반 없음으로 반영됐다. 얼룩 없는 테이블은 컵만 옮겨도 정리가 끝났다.

소모품 품절과 반납대 컵·얼룩이 있는 별도 확인용 백업도 불러왔다. 완성된 음료 전달은 품절 상태에서도 성공했고, 소모품이 음수로 줄지 않으며 보충 안내를 표시했다. 이 전달은 반납대의 컵을 2개에서 3개로 늘렸다. 세 컵을 직접 회수해 분리수거함에 옮기고 반납대를 닦아 컵 0개·오염 없음·청소 작업 없음으로 끝냈다. 브라우저에서 애플리케이션 오류는 발견하지 않았다. 확인용 백업과 캡처는 저장소 밖에 두었고 자동 테스트 코드는 추가하지 않았다.

## 손님 동선 확인

한 손님은 입구에서 POS로 이동해 도착한 뒤 주문을 받는다. 주문표 출력 후 픽업대로 이동하고, 수령 뒤 컨디먼트 이용·착석·10초 체류·컵 반납 또는 테이블 방치·퇴장을 마친다. 앞 손님이 출구에 도착해야 다음 손님 ID와 주문 번호를 만든다. 진행 단계, 경로 지점, 위치·방향, 체류 시간과 반납·오염·설탕 이용 의도를 저장한다. 매장 현황에서도 현재 손님과 이용 단계를 확인할 수 있다.

브라우저의 새 근무에서 입장 중 POS 접수가 비활성화되는 것을 확인했다. 이동 중 저장·새로고침 후 같은 손님 ID·위치·단계가 복원됐다. 콜드 브루를 직접 제조해 픽업 대기 중인 손님에게 전달했고, 반복 확인에도 판매 1잔·매출 5,000원만 기록됐다. 전달 직후에는 소모품·반납 컵이 그대로였고, 실제 컨디먼트 이용 후 냅킨·빨대가 각각 1개 줄었다.

테이블에 앉은 상태를 저장·복원하고 남은 체류 시간을 이어갔다. 이 손님은 테이블에 컵을 남기는 경우였으며, 10초 체류 후에만 컵 1개가 생겼다. 퇴장 후 새 ID의 002번 손님이 입장하고 요청은 HOT 라떼로 바뀌었다. 주문 전 마감한 두 번째 손님은 판매나 소모품 사용을 추가하지 않고 퇴장했다.

반납과 청소가 겹치는 별도 확인용 백업에서도 확인했다. 마감 중인 손님이 컵을 반납하면서 진행 중인 닦기에 새 오염이 생겼고, 닦기 확인 후 새 컵 회수 단계로 이어졌다. 컵·쓰레기를 정리하고 손님이 모두 나간 뒤 결산할 수 있었다. 다음 날에는 시작 잔액 55,000원·판매 0잔과 새 입장 상태로 이어졌고, 이전 손님의 반납이나 판매가 다시 반영되지 않았다. 브라우저 애플리케이션 오류는 발견하지 않았다.

## 첫 근무 안내와 녹음 기반 작업음

`FirstShiftGuide`는 게임 상태에서 현재 목표·도구·운반·부족 재료·라벨·보관 안내를 계산한다. 주문 001 콜드 브루와 002 HOT 라떼 전달 후 자동으로 접히며 H로 복습할 수 있다. 별도 튜토리얼 진행 필드나 업무 잠금은 추가하지 않는다. 작업 패널 안에서는 한 줄 행동 위주로 줄이고, 좁은 화면에서는 안내 제목·보조 문구를 줄여 제조 조작을 가리지 않도록 한다.

음소거·음량·안내 표시는 `preferences.ts`에서 검증하며 기존 IndexedDB의 별도 `preferences` 키에 저장한다. 게임의 `current`·`previous` 백업과 분리하고 기존 `GameState` 형식은 유지한다. 설정을 읽지 못하면 기본 음소거·35%·안내 켜기로 시작하며 저장 실패는 설정 화면에 표시한다.

`work-sounds.ts`는 사용자가 소리를 켜거나 근무를 시작·재개·미리 듣기 할 때 Web Audio를 활성화한다. 기본 음소거 상태에서는 오디오 컨텍스트나 음원 요청을 만들지 않는다. 원본 녹음을 가공한 WAV 9개는 약 453KB이며 처음 필요할 때 같은 출처에서 읽고 디코딩해 재사용한다. 단발 작업음은 최대 3개, 연속음은 1개로 제한하고 짧은 페이드를 적용한다. 펌프·컵·얼음·계량 목표 구간·확인·완료·전달·오류는 실제 행동 전후의 변화로 결정하며, 지속음은 현재 누르기 입력이나 가까운 샷·스팀 장비 작업을 따른다.

일시정지·백그라운드·포커스 이탈·음소거·음량 0%·백업 가져오기는 재생을 중단한다. 손을 떼면 붓기·닦기 입력도 중단한다. 재개할 때는 현재 장비 작업만 다시 연결하고 저장된 지난 메시지를 재생하지 않는다. 앱 정리 시 오디오 노드·다운로드·컨텍스트도 정리하며 로딩·재생 실패는 미리 듣기로 재시도할 수 있다. 근거: [Web Audio 권장 사항](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices), [AudioContext.resume](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/resume), [AudioContext.close](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/close). 음원 출처·라이선스·가공은 [크레딧](../../apps/cafe/public/audio/CREDITS.md)에 기록한다.

브라우저에서 초기 콜드 브루를 직접 접수·계량·얼음 투입·전달했고 안내가 다음 행동으로 이어졌다. 기본 음소거 시 음원 요청이 없고, 켠 뒤 9개 음원 디코딩과 재생 노드가 생성되는 것을 확인했다. 붓기 입력 해제와 일시정지 후 연속음이 멈췄으며, 음량 60%·안내 숨김을 저장하고 새로고침해 설정과 게임 상태가 복원되는 것도 확인했다.

라떼의 우유 부족·원팩 개봉·라벨·냉장 보관, 우유 계량·스팀 완료, 폼 펌프 계량·블렌딩·라벨·보관과 두 번째 음료 전달은 저장소 밖의 확인용 백업을 불러와 수동 조작했다. 스팀 중 포커스 이탈 시 모든 음원이 종료됐고, 음량 0%에서는 계량·확인을 해도 재생 노드가 생기지 않았다. 음소거 상태의 잘못된 보관 위치 안내도 화면에 남았다. 두 번째 전달 후 안내 자동 접힘과 H 복습 열기를 확인했다. 1280×720·1024×640에서 POS 주문 버튼과 안내 배치를 확인했으며 애플리케이션 오류는 발견하지 않았다. 확인용 백업·계측·캡처는 제품 코드에 포함하지 않았다.

## 자료 갱신 연결 확인

`reference-links.ts`는 현재 플레이하는 세 음료, 폼·바모카·콜드 브루 준비와 초기 재료의 품질 기준만 연결한다. 메뉴·온도·배합 이름을 유일하게 찾고 단계의 재료·대상·단위·순서를 확인한다. 배열 위치나 행 번호는 조회 키가 아니며, 물리적인 행을 옮겨도 연결된 원본 위치를 따라간다. 기존 게임이 지원하는 실제 제조 순서를 바꾸는 자료는 오류로 표시해 작업대·도구·저장 단계의 의미를 먼저 검토하게 한다.

음료의 샷·펌프·드리즐·토핑 목표량은 각 HOT·ICED 자료에서 읽는다. 펌프 ml도 해당 음료의 메모에서 읽고, 조작 목표와 재고 소비가 같은 수량을 사용하도록 했다. 폼의 크림·우유·소스·블렌딩은 이름으로 연결하며 준비 가이드의 바모카 봉·온수 L과 콜드 브루의 추출 시간도 검증한다. 콜드 브루 작업 시간과 창고·첫 근무 안내는 같은 값을 표시한다.

품질 표는 파일·시트·품목명과 개봉후·소분후·제조후·추출후 조건을 구분한다. 바모카와 콜드 브루는 준비 자료와 품질 표의 보관·기한이 일치해야 한다. 월·당일처럼 현재의 일/시간 계산에 맞지 않는 표기는 자료 확인 오류로 처리한다. 컵 기준선의 ml 환산·수율·샷당 원두량·원팩 규격과 바모카 원팩의 임시 7일은 별개로 유지한다.

가져오기에서는 여섯 시트의 열 제목을 확인한 뒤 신규 변환 결과를 같은 연결 함수로 검증한다. 검사·포맷을 마치기 전에는 기존 생성 JSON을 쓰지 않는다. 전체 음료 개수 14·배합 개수 6의 고정 제한은 제거했으며, 자료의 새 메뉴가 자동으로 플레이 메뉴에 노출되지는 않는다. `check:references`와 `dev`·`build`는 원본 엑셀 없이 생성 JSON을 검사한다. 별도 테스트 프레임워크나 테스트 전용 구조는 추가하지 않았다.

현재 원본을 재생성한 JSON은 기존 파일과 동일했다. 변경 전 카탈로그와 대조해 조작 목표·재고 소비·준비 배합·보관·기한이 유지됨을 확인했다. 메모리상의 자료 사본에서 메뉴·단계 배열을 뒤집고 행 번호를 옮겨도 동일한 수량에 연결됐으며, ICED만 2샷·4펌프·펌프당 12ml로 바꾼 경우 HOT은 1샷·3펌프를 유지했다. 누락·중복·샷 단위 변경·빈 펌프 수량·단계 의미/순서 변경·폼 단위 변경·바모카 기한 충돌·미지원 기한 단위가 각각 해당 자료 오류로 표시됐다. 이 사본은 원본이나 생성 파일에 반영하지 않았다.

브라우저에서는 저장소 밖의 확인용 백업으로 HOT·ICED 소스 단계에서 각각 3회 펌핑 후 F로 확인했다. 두 경우 모두 글레이즈드 소스 30.6ml를 소비하고 각자의 다음 단계로 이어졌다. 우유 원팩 개봉 후 냉장·48시간 라벨과 콜드 브루 20시간 표시·실제 작업 시간을 확인했다. 애플리케이션 오류는 없었고, 저장 형식은 변경하지 않았다.

## 날짜 기한과 배합 원재료 기한 확인

2026-09-24 사용자는 모든 N일 기한에 시작일을 포함하는 달력 계산을 적용하고, 폼·바모카의 기한을 투입한 원재료의 가장 빠른 기한으로 제한하도록 결정했다. 컵 ml·수율·원팩·원두량·스팀·세척의 미확정 수치는 기존 임시값을 유지한다. 원본 자료를 변경하지 않고 `Lifetime`에 일·시간 단위를 보존해 새 배치 생성·원팩 개봉에서 `expiryAt`을 호출한다. 자료 대조에서도 1일과 24시간을 같은 규칙으로 취급하지 않는다. 게임의 가상 날짜는 기존 UTC 표현을 유지하며 사용자의 PC 시간대에 영향을 받지 않는다.

재료 소비는 기존의 기한이 빠른 순서를 유지하고 실제로 사용한 양이 있는 배치들의 가장 빠른 만료 시각을 반환한다. 준비 상태의 `ingredientExpiresAt`에 누적해 원래 배치가 모두 소모돼 없어져도 저장·복원할 수 있다. 제조 완료 시 기본 만료 시각과 이 값의 최솟값을 완성 배치에 기록한다. 시간 진행에서는 장비 완료를 실제 완료 예정 시각에 처리한 다음 현재 시각의 준비 만료를 확인한다. 만료와 완료가 같으면 완성하지 않으며, 만료 전에 완성됐지만 현재 시각에는 기한이 지났다면 완성 기록과 만료된 배치를 함께 유지한다.

계량·혼합·블렌딩 중 투입 원재료가 만료되면 추가 소비와 준비 작업을 중단하고 폐기를 안내한다. 장비 작업을 제거하고 폐기할 때 이미 투입한 재료를 폐기량에 기록하며 예약한 피처를 세척 대상으로 돌려놓는다. 완성 배치의 라벨·보관도 만료를 연장하지 않는다. 준비 HUD에는 투입 원재료 기한을, 라벨에는 사용 불가가 시작되는 만료 시각과 원재료에 따라 짧아진 이유를 표시한다.

`ingredientExpiresAt`은 새 준비에는 null로 시작하고 소비 시 기록한다. 값이 없는 준비 기록은 게임 전체를 초기화하거나 과거 소비를 추정하지 않고 해당 배합의 폐기·재준비를 안내한다. 창고를 통한 라벨·보관으로도 이 상태를 우회하지 못한다. 이미 저장된 배치의 절대 만료 시각은 유지하고 새 개봉·제조부터 날짜 규칙을 적용한다. 저장 버전·마이그레이션은 추가하지 않았다.

날짜 계산은 9월 1일 15시 개봉 우유 → 9월 3일 0시, 7일 기한 원두 → 9월 8일 0시, 24시간 휘핑크림 → 9월 2일 15시를 확인했다. 월말과 윤년의 2월 29일을 지나는 경우도 확인했다. 브라우저에서 우유 원팩을 실제로 개봉하니 9월 3일 00:00 라벨과 날짜 기준 설명을 표시했다.

브라우저에서 10시 만료 크림 100ml와 11시 만료 크림 300ml가 있는 확인용 백업을 불러와 약 200ml를 계량했다. 먼저 쓰인 100ml 배치가 사라진 뒤 저장·새로고침해도 준비의 10시 기한은 유지됐다. 우유·7펌프·블렌딩까지 마친 폼 450ml의 만료 시각도 10시였고 원재료 기한 설명을 표시했다. 별도 만료 상황에서는 블렌딩이 중단됐고 F로 폐기한 뒤 크림 200ml·우유 50ml·소스 71.4ml가 폐기로 기록됐으며 피처가 세척 대상으로 돌아갔다. 완료보다 먼저·동시에 만료되는 경우, 완료 직후 현재 시각 전에 만료된 경우와 기한 기록이 없는 준비의 폐기 안내도 확인했다. 확인용 데이터는 저장소 밖에 두었고 테스트 코드는 추가하지 않았다.
