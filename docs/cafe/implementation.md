# 카페 성능 측정 기록

사용자와 정한 목표 환경은 데스크톱 Chrome·Edge, FHD(1920×1080), 60fps다. 각 기록은 해당 날짜의 코드와 측정 환경에 한정하며 이후 변경의 성능을 보장하는 수치로 사용하지 않는다.

## 초기 렌더링 준비 (2026-09-30)

첫 탐색에서만 발생하는 프레임 지연을 확인했다. 매장 모델은 코드로 생성되지만, 장면 생성 완료와 GPU 준비 완료는 다르다. 기존에는 장면 생성 직후 시작 버튼을 활성화했으며 시야 밖 재질·도형·텍스처는 첫 렌더링 때 준비했다.

`world/prepare-scene.ts`에서 장면 수명에 속하는 준비 작업을 처리한다.

- 현재 저장 상태의 시각 표현을 먼저 반영한다. 글꼴 로딩에 따른 캔버스 라벨 재그리기가 끝난 뒤 셰이더를 `compileAsync()`로 준비하고 텍스처를 업로드한다. 텍스처 사이에는 4ms의 CPU 작업 예산을 확인해 다음 프레임으로 양보한다. 단일 WebGL 호출의 실행 시간을 4ms로 제한한다는 의미는 아니다.
- 이미 생성된 숨은 소품과 시야 밖 오브젝트도 64개 메시 단위로 실제 렌더링한다. 원래 카메라·조명·그림자·프레임버퍼 설정을 사용한다. 임시로 바꾼 표시 여부·레이어·프러스텀 컬링은 `finally`에서 복원한다.
- 원래 장면과 그림자를 다시 그린 뒤 GPU fence를 대기 시간 0으로 조회한다. GPU 작업이 끝나면 캔버스를 표시하고 시작 버튼을 활성화한다. 준비 중에는 게임 렌더링 루프를 시작하지 않는다.
- 장면 해제 시 대기 중인 프레임을 취소하고, 준비 완료 콜백이 해제된 장면의 루프나 React 상태를 다시 켜지 않도록 한다.

프로덕션 빌드를 localhost에서 실행하고 Chrome 150·Apple M2 Pro·ANGLE Metal, 실제 canvas 1920×1080에서 확인했다. 새 저장에서 오른쪽 방향키로 5.2초 회전하고, 이어서 같은 방향으로 5.2초 더 회전했다. 브라우저에 임시 계측을 넣어 rAF 간격과 WebGL 호출 수를 기록했다. 아래 전후 실행은 전 구간에서 문서가 표시되고 포커스가 유지된 것을 확인했다.

| 측정 항목                            |   변경 전 |   변경 후 |
| ------------------------------------ | --------: | --------: |
| 셰이더 프로그램 연결 (`linkProgram`) |       9회 |       0회 |
| 텍스처 업로드 (`texSubImage2D`)      |      92회 |       0회 |
| 도형 버퍼 업로드 (`bufferData`)      |   1,196회 |       0회 |
| 25ms 초과 프레임                     |       1회 |       0회 |
| 최대 프레임 간격                     |    33.4ms |    16.8ms |
| 페이지 이동부터 시작 버튼 준비까지   | 약 1.53초 | 약 2.66초 |

변경 후 첫 회전과 반복 회전의 프레임 p95는 각각 16.8ms·16.7ms였고, 별도 새 브라우저 프로세스에서도 첫 회전의 최대 간격 16.8ms·추가 GPU 초기화 0회를 확인했다. 변경 전 최초 관찰에서는 1200×675에서 최대 332.9ms의 지연이 있었지만 같은 브라우저에서 재실행하면 크게 줄었다. 드라이버 캐시를 완전히 통제하지 않았고 디스플레이 주사율도 실행별로 달라, 최대 프레임 시간의 개선 배율이나 보편적인 FPS 증가율로 해석하지 않는다. 재현 가능한 핵심 변화는 첫 탐색 구간의 GPU 초기화를 시작 전으로 옮긴 것이다.

개발 장면 API로 1층·2층·루프탑의 높이에서 각각 8방향으로 시점을 전환했을 때도 추가 프로그램 연결·텍스처·버퍼 업로드가 없었다. 준비 시작 직후와 분할 렌더링 도중 장면을 해제하면 캔버스가 제거되고 추가 그리기·업로드가 발생하지 않았다.

초기 대기 시간과 미리 확보하는 GPU 자원은 늘어난다. 계측한 초기 `bufferData` 데이터 합은 약 14.1MB에서 26.5MB로 늘었으며, 이는 임시 자원까지 포함한 업로드 합으로 실제 VRAM 사용량은 아니다. 화질·해상도·그림자 설정은 유지한다. 범위는 시작할 때 존재하는 오브젝트와 현재 저장 상태이며, 플레이 중 새로 생성되는 컵·도구의 최초 생성 비용이나 저사양 Windows·실제 모바일 기기의 성능까지 보장하지 않는다.

API 근거: [Three.js 셰이더 사전 컴파일](https://threejs.org/docs/pages/WebGLRenderer.html#compileAsync), [텍스처 초기화](https://threejs.org/docs/pages/WebGLRenderer.html#initTexture), [WebGL GPU 완료 상태 조회](https://developer.mozilla.org/en-US/docs/Web/API/WebGL2RenderingContext/clientWaitSync).

## 표현과 성능 측정 (2026-09-25)

프로덕션 빌드를 localhost에서 실행해 Apple M2 Pro·Metal, Chrome 154·Edge 154, 실제 canvas 1920×1080·DPR 1에서 확인했다. Edge는 [공식 Stable 배포 정보](https://edgeupdates.microsoft.com/api/products?view=enterprise)의 패키지를 임시 폴더에서 풀어 실행했다. 측정은 requestAnimationFrame 간격과 실제 WebGL 그리기·버퍼 전송 호출을 사용했으며 그리기 수에는 그림자 패스가 포함된다. 확인용 저장의 재료·손님·시점은 전후 동일하게 맞췄다.

| 측정 항목                        | 변경 전                      | 변경 후                       |
| -------------------------------- | ---------------------------- | ----------------------------- |
| 기본 근무 장면 그리기            | 프레임당 457회               | 약 263회                      |
| 고정 ICED 컵 장면 그리기         | 프레임당 443회               | 약 256회                      |
| 멈춘 컵의 액체 버퍼 전송         | 초당 180회·414KB             | 0회·0KB                       |
| 시작·일시정지 화면의 지속 그리기 | 시작 화면에서 프레임당 457회 | 상태·크기 변경이 없으면 0회   |
| Chrome 기본·컵 장면              | 60fps, 프레임 p95 약 16.7ms  | 60fps, 프레임 p95 16.7~16.8ms |

Chrome에서 컵을 들고 60초 동안 회전하며 3,600프레임을 기록했다. 평균 60fps·프레임 p95 16.7ms, 25ms 초과 0회, 멈춘 내용물의 버퍼 재전송 0회였다. Edge의 첫 실행 직후 5초 구간은 초기 지연 3회로 평균 50.5fps였고, 준비 후 10초 구간은 60fps·p95 16.7ms·25ms 초과 0회였다. Edge의 60초 유지 구간도 3,600프레임·60fps·p95 16.7ms·25ms 초과 0회였으며, 별도 15초 방향키 회전 구간은 평균 59.3fps·p95 16.7ms·25ms 초과 1회였다. Edge에서도 일시정지 중 그리기·버퍼 전송은 0이었다.

로컬 HTML·스크립트 로딩은 약 31~100ms 범위였으나 네트워크나 운영 캐시 성능을 의미하지 않는다. 이 측정은 위 기기·브라우저·짧은 반복 플레이 구간의 확인이며 저사양 Windows, 장시간 전체 근무, 고배율 화면까지 60fps를 보장하지 않는다.

## 빌드 청크 분리

2026-09-25 Vite 8.3.0 빌드에서 React 계열·Three.js 코어·렌더러의 청크를 분리한 전후 결과다. 라이브러리 청크를 나눈 목적은 앱 변경에 따른 캐시 갱신 범위를 줄이고 기본 500KB 경고 기준을 지키는 것이다.

| 청크            |   변경 전 바이트 | 변경 후 바이트 | 변경 후 gzip 바이트 |
| --------------- | ---------------: | -------------: | ------------------: |
| 메인            |          520,844 |        330,497 |              81,563 |
| 장면            |          584,274 |         42,475 |              16,708 |
| React 계열      |      메인에 포함 |        189,588 |              59,604 |
| Three.js 코어   |      장면에 포함 |        191,004 |              51,880 |
| Three.js 렌더러 |      장면에 포함 |        352,317 |              84,771 |
| Bundler runtime | 기존 청크에 포함 |            589 |                 368 |

수치는 minify한 실제 출력 파일의 UTF-8 바이트 길이다. 가장 큰 청크는 584,274바이트에서 352,317바이트로 줄었다. `chunkSizeWarningLimit` 변경이나 경고 필터 없이 Vite 기본 500KB 기준을 통과한다.

JS 파일은 2개에서 6개가 되고, 전체 JS 크기는 1,105,118바이트에서 1,106,470바이트로 거의 같다. 이번 변경은 개별 청크와 캐시 경계를 정리한 결과다. 전체 전송량 감소나 실행 중 프레임 속도 향상을 의미하지 않는다.
