# 카페 게임 구현 준비

현재 구현 이후의 우선순위·범위·완료 기준은 [후속 작업 분석](./next-steps.md)을 따른다. 2026-09-25 전체 코드 진단과 리팩터링 결과는 [코드 구조 진단](./code-health.md)에 기록한다. 아래 구현 순서는 기반 작업의 순서와 완료 기록이다.

과거 확인 기록에 남아 있는 500KB 초과 경고는 후속 [빌드 청크 분리](#빌드-청크-분리)에서 해결했다. 과거 플레이 기록의 수량·조작값은 당시 확인 결과이며 현재 제조 규칙은 [구조화 제조 자료](#구조화-제조-자료)와 [제조 자료 운영](./recipe-data.md)을 따른다. 최신 변경의 검증 결과를 과거 기록에서 추정하지 않는다.

## 착수 조건

게임의 목적, 핵심 업무, 초기 메뉴와 시간 흐름은 정해졌다. 실제 계량 용기의 형상, 일부 장비 시간, 세척 세부와 날짜 계산 관례는 추가 확인이 필요하다.

사용자에게 확인한 착수 결정:

- 기존 프로젝트 구조에 얽매이지 않고 구현에 맞는 방식을 선택한다. `apps/cafe`에 Vite + React + TypeScript + Three.js를 사용한다.
- 제공한 자료를 공개해도 된다. 원본 배합·품질 기준을 변환한 데이터를 소스와 빌드에 포함한다.
- 초기에는 미확인 절차를 임시 규칙으로 표시했다. 이후 제조 자료 정리에서 원문에 없는 횟수·시간을 제거하고, 기존 물리 추정치는 승인된 재고 계산에만 남겼다.

## 저장소에서 확인한 기본값

- Bun workspaces의 `apps/*`에 독립 앱을 둔다.
- 기존 게임 앱은 `@sobok/next-config`의 정적 내보내기를 사용하지만 이 앱은 사용자 허용에 따라 Vite의 브라우저 전용 정적 빌드를 사용한다.
- React는 POS·운영 UI, Three.js는 매장·시점·상호작용을 담당한다. 프레임별 카메라 처리는 React 렌더와 분리한다.
- React UI는 Tailwind CSS v4와 공식 Vite 플러그인으로 스타일링한다.
- 원격 데이터베이스, API route, Server Action은 이 게임에 필요하지 않다.
- Cloudflare 원격 변경은 별도 배포 단계다. 이 작업에서는 로컬 구현과 빌드 확인을 진행한다.
- 로직은 먼저 앱 안의 호출부 근처에 두고, 다른 앱과 실제로 재사용할 때 공용 패키지를 검토한다.

## UI 스타일

- `apps/cafe/vite.config.ts`에서 `@tailwindcss/vite`를 연결한다. `src/style.css`의 `source('.')`는 클래스 탐색 기준을 이 앱의 소스 디렉터리로 고정한다.
- 색상·글꼴·반복되는 글자 크기·그림자·화면 너비 기준은 `@theme`으로 정의한다. 낮은 화면의 HUD 배치는 `compact` 높이 변형을 사용한다.
- 각 JSX 요소에 유틸리티 클래스를 작성한다. 기존 화면 클래스나 `@apply` 기반 컴포넌트 스타일은 두지 않는다. Three.js가 생성하는 canvas는 호스트의 하위 요소 변형으로 크기를 지정한다.
- 반복되는 일반 버튼은 `shared/ui/Button.tsx`, 작업 HUD·제목·조작 버튼·게이지는 `shared/ui/WorkControls.tsx`에서 공유한다. 재고·소모품 목록의 동일한 버튼은 `Button.tsx`의 `InventoryButton`을 사용한다. 버튼의 색상과 크기는 명시적인 variant·size로 선택하고, 호출부의 `className`은 배치용으로 사용한다.
- 클래스 이름의 일부를 동적으로 이어 붙이지 않는다. 상태는 완전한 클래스 문자열 또는 `data-*`·이름 있는 `group` 변형으로 표현한다. 재고 펼침 상태는 네이티브 `details`의 `open`을 따른다.
- 실행 중 계산되는 게이지 너비·목표 위치는 인라인 스타일로 전달한다. 정적인 배치와 장식은 Tailwind로 관리한다.
- Preflight의 초기화를 기준으로 여백·목록·타이포그래피를 요소에 명시한다. 전역 CSS에는 테마와 기본 요소 규칙만 두며, 키보드 `focus-visible`과 동작 줄이기 설정을 반영한다.

참고: [Vite 설치](https://tailwindcss.com/docs/installation/using-vite), [테마 변수](https://tailwindcss.com/docs/theme), [클래스 탐색](https://tailwindcss.com/docs/detecting-classes-in-source-files), [유틸리티·반복 스타일·인라인 값](https://tailwindcss.com/docs/styling-with-utility-classes), [Preflight](https://tailwindcss.com/docs/preflight), [상태 변형](https://tailwindcss.com/docs/hover-focus-and-other-states), [W3C 키보드 포커스 표시](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html).

## 구현 순서

### 1. 공간과 입력

매장, 작업대, 물체, 첫 시점, 이동·충돌·시선 상호작용을 만든다. 시작·일시정지와 작업 안내를 연결한다. 메뉴 UI와 게임 입력이 동시에 동작하지 않도록 한다.

### 2. 주문에서 전달까지

손님 요청과 POS 입력을 별도로 저장한다. 컵 준비, 단계별 제조, 재료 소비, 완성 판정, 전달, 재제조를 연결한다. 임시 규칙은 설정에 모으고 실제 기준과 구분한다.

### 3. 지원 업무

사용한 도구가 세척 대상으로 이어지고, 세척한 도구를 제자리로 돌려놓게 한다. 테이블 상태, 재고 보충, 용기별 잔량·라벨 확인을 연결한다. 지원 업무 없이 제조만 무한 반복할 수 없게 한다.

### 4. 시간과 근무 마감

게임 시계, 신규 주문 마감, 남은 주문 처리, 정리, 결산, 다음 날을 연결한다. 기한과 장시간 준비 작업은 같은 게임 시계를 기준으로 한다. 일시정지와 백그라운드 상태에서는 진행하지 않는다.

### 5. 저장과 복구

IndexedDB에 현재 상태를 저장한다. 입력 검증, 저장 실패 안내, 이전 정상 저장, 파일 백업·복원을 제공한다. 저장 버전 관리와 이전 구조의 마이그레이션은 사용자 요청에 따라 구현하지 않는다. 탭 간 상태 동기화는 구현하지 않고 현재의 Web Locks 중복 실행 제한을 유지한다. 자동 잠금 인계나 잠금 획득 시점 변경도 추가하지 않는다. 저장 완료 전 페이지를 닫는 경우는 필요한 브라우저 확인 항목으로 둔다.

## 완료 기준

브라우저에서 들어가 이동하고, 주문 한 건을 접수·제조·전달할 수 있다. 그 과정에서 재료와 도구 상태가 바뀌고 청소·설거지·정리·보충으로 회복된다. 근무를 마감하고 다음 날 또는 저장한 상태로 이어진다.

소스의 타입 검사와 빌드, 실제 브라우저 플레이로 동작을 확인한다. 테스트 코드 작성은 이번 범위에 포함하지 않는다.

## 추후 확정할 실제 절차

컵·피처의 계량선 형상, 샷 이관, 원팩의 포장 규격, 배합 용기와 혼합 시간, 스팀 모드, 세척·건조 순서, 기한 계산 관례, 장시간 추출의 후속 처리다. 첫 플레이 버전의 단순화는 [구현 규칙](./prototype-rules.md)에 기록한다.

## 현재 파일 구조

2026-09-25 사용자 합의에 따라 기존 `game`·`ui`의 구분을 업무 중심으로 다시 구성했다. 현재 책임 경계와 변경 진입점은 [코드 아키텍처](./architecture.md)를 따른다.

- `apps/cafe/src/app/`: 부팅, 화면 구성, 입력·3D·저장·오디오 연결. 작업대 패널과 도움말은 업무별 화면을 조합한다.
- `apps/cafe/src/simulation/`: 전체 상태 스키마, 행동 union, 초기 상태, 공통 점유 조건, 상태 복사·발행과 시간 처리 순서.
- `apps/cafe/src/features/`: 응대·제조·부재료 준비·콜드 브루·재고·세척·청소·근무별 규칙, 행동, 화면, 도움말과 3D 표현.
- `apps/cafe/src/world/`: 매장 전체 장면, 정적 매장·충돌 영역, 플레이어 이동·포인터 잠금, GPU 자원 수명.
- `apps/cafe/data/`: 제조 문서·재료·장비·용기·메뉴·품질과 별도의 재고 추정 JSON.
- `apps/cafe/src/content/`: 제조 스키마·카탈로그·실행 계획, 재고 환산 경계, 작업대·고객 정의와 기한 해석.
- `apps/cafe/src/shared/`: 반복 UI·3D 자산, 표시 형식, 식별자와 도움말 값 타입.
- `apps/cafe/src/main.tsx`, `style.css`: 앱 진입점과 Tailwind 테마·기본 스타일.
- `apps/cafe/scripts/`: `check-recipes.mjs`의 전체 제조 자료와 판매 조합 검사.

아래 완료 기록의 단독 파일명은 해당 작업을 진행한 시점의 이름이다. 현재 위치는 위 아키텍처 문서를 기준으로 찾는다.

## 직접 제조 구현 확인

2026-09-24 기준으로 준비된 주문·재료 상태에서 브라우저의 이동·집기·붓기·펌핑 조작을 사용해 콜드 브루, HOT·ICED 블랙 글레이즈드 라떼의 제조와 전달을 확인했다. 판매액·재고 소비·피처 상태가 반영되고, 네 번째 소스 펌핑은 오류로 기록되며 폐기해도 사용한 재료는 반환되지 않는다.

계량 도중 저장 후 새로고침, 진행 중 작업의 완료, 창 포커스 이탈 시 투입 정지, 제조 HUD의 마우스 누름·해제를 확인했다. 타입 검사와 Vite 빌드를 통과했고 자동 테스트 파일은 추가하지 않았다. Three.js 장면 청크에는 Vite 기본 500kB 크기 경고가 남아 있다.

직원 동선은 카운터 안쪽으로 수정했다. 장비 전면·컵·추출 위치와 POS가 직원 쪽을 향하고, 픽업대·세척대·도구 선반도 같은 업무 공간에 연결된다. 직원 통로에서 콜드 브루 주문 접수부터 제조·전달까지, 샷 추출과 세척·정리, 고객 쪽 제조 차단과 카운터 충돌을 브라우저에서 확인했다. 새 근무는 직원 통로에서 시작하고 저장한 근무는 저장 위치에서 이어진다.

부재료 준비는 폼·바모카의 직접 계량·혼합·라벨·보관까지 연결했다. 브라우저에서 폼 7펌프와 25초 블렌딩, 바모카 원팩·온수·젓기, 준비 도중 저장 복원, 잘못된 보관 위치 안내와 올바른 보관 후 재고 반영을 확인했다. 원팩은 개봉·라벨 단계에서 사용 가능량이 늘지 않고 보관 완료 후 증가한다. 사용한 피처는 세척 대상으로 돌아가며, 과다 계량 폐기와 만료 배치 차단도 확인했다.

피처 세척은 문지르기·헹구기·집기·운반·선반 정리로 연결했다. 세척 중 손을 떼면 멈추고 저장 후 같은 진행량으로 이어진다. 세척 중인 피처, 세척 완료 대기 피처와 들고 있는 피처를 구분해 중복 회수하지 않는다. 다른 작업대에 컵을 두면 혼합 작업대의 청소 메뉴에 접근할 수 있고, 빈손이 필요한 업무에는 컵을 내려놓으라는 안내를 표시한다. 재접속 시 저장된 카메라 방향도 유지한다.

작업대에 컵·부재료·세척 작업이 남으면 마우스 시점 복귀까지 막던 조건을 제거했다. 근무 시작·재개, WASD 이동, 컵·피처 집기, 작업 종료 시 마우스 고정을 요청하고, 제조·준비·세척 버튼을 사용하는 동안에는 커서를 해제한다. 작업 시작 시 고정 요청과 해제 요청이 겹치지 않도록 분리했으며 입력 모드를 하단에 표시한다. 브라우저에서 진행 중인 작업을 복원한 뒤 재개·이동·컵 집기·세척 취소의 고정 요청과 작업 시작 시 커서 유지, 기존 작업 상태 보존을 확인했다. 검증용 macOS Chrome은 네이티브 포커스 제한으로 `requestPointerLock`을 거절해 실제 고정 후 마우스 이동은 확인하지 못했으며, 이 환경에서는 대체 조작 안내가 표시됐다. 타입 검사와 빌드는 통과했다.

최신 초기 상태에서 브라우저 키보드·화면 버튼으로 콜드 브루 → HOT 라떼 → ICED 라떼 → 마감 → 다음 날을 완주했다. 추가 재료나 도구를 미리 넣지 않고 초기 원팩 개봉·라벨·보관과 폼·바모카 직접 준비를 수행했다. HOT 소스 과다 펌핑으로 컵 한 개를 폐기한 뒤 재제조했다. 결과는 전달 3잔, 매출 18,000원, 청소 6회, 세척 5회, 재제조 컵 1개였다. 마감 시 피처는 깨끗함 3개·오염 0개·세척 완료 대기 0개이고 세척/운반 작업이 남지 않았다.

20시간 콜드 브루 추출을 시작하고 마감한 뒤 다음 날 3,000ml 배치가 생성되는 것을 확인했다. 다음 날 만료된 휘핑크림은 사용 가능량 0으로 표시됐고 폐기할 수 있었다. 후방 컵 24개에서 6개를 보충해 다음 근무를 준비했다. 이 확인용 근무의 잔액은 매출과 추출 준비비 9,000원을 반영한 59,000원이었다.

첫 구현은 로컬 빌드까지 진행했다. 운영 배포는 Vite가 생성하는 `dist`를 Cloudflare Workers Static Assets로
제공한다. GitHub Actions의 `Cafe Deploy` 또는 `Production Deploy`가 Worker를 배포하고,
`sobok-ops`의 `account-workers` HCP Terraform workspace가 `cafe.sobok.cc` custom domain을 소유한다.
스테이징은 구성하지 않는다.

## HUD 정보 위계 정리

[화면 정보 설계](./hud.md)를 따른다. 상단의 근무 상태·접수한 주문, 하단의 시선 대상 또는 작업 조작, 필요할 때 여는 도움말·운영 화면으로 나눈다. 시선 대상도 운반 중인 물건도 없으면 하단을 비운다. 게임 소개·분위기 문구·상시 단계 안내·마우스 모드·정상 조작 알림을 제거했다.

작업명·계량값·버튼은 각각 무엇을 하는지, 얼마나 진행했는지, 어떻게 조작하는지를 맡는다. 목표 구간에 들어오면 강조만 바뀌며 누르는 입력을 끊지 않는다. H는 시간을 멈추고 현재 작업·레시피·조작법을 표시한다. 닫으면 열기 전 작업 패널을 복원한다. M은 할 일을 먼저 보여주고 운영 기록은 별도 선택으로 제공한다. 설정과 저장 관리는 Esc 메뉴에서 펼친다.

재고는 품목·사용 가능량과 부족·만료·보관 대기만 요약한다. 개봉·라벨·입고와 배치 기한은 품목별 상세에, 원재료 기한은 H 도움말에 둔다. 오류와 저장 실패는 계속 표시하며 일반적인 상태 변화는 게이지·주문표·물건의 변화로 전달한다.

매장·포장 주문과 종류별 컵·세척 모델을 현재 HUD에 통합했다. POS는 이용 방식을 두 선택지로 표시하고 선택지에 포커스가 있어도 H·M·Esc를 사용할 수 있다. 필요한 컵이 없는 보관대에서 E를 누르면 재고 패널을 연다. 컵 종류·사용 가능량을 먼저 보여주고 일회용 보충·입고는 상세에 둔다. 세척대에는 세척·보관 대기가 있는 용기만 표시하며, H 도움말도 회수·세척·보관 대기를 구분한다. 도구를 놓고 확인할 차례에는 도구를 다시 집는 버튼을 숨기고, 리드는 부착 후 F 확인만 강조한다.

현재 작업 트리의 타입 검사·자료 검사·프로덕션 빌드, 변경한 UI의 Biome 검사와 브라우저 확인을 마쳤다. 1280×720에서 POS 이용 방식의 잘못된 입력·수정, 매장 콜드 브루 직접 계량·리드 없이 전달, 반납 유리잔 회수·세척·보관대 반납을 확인했다. 판매 1잔·5,000원이 반영되고 유리잔은 깨끗한 4개로 돌아왔다. 확인용 저장 사본으로 고객 이동 시간을 경과시키고 직원 위치를 옮겼으며 컵의 회수·세척·정리는 화면 조작으로 진행했다.

별도의 포장 주문 사본에서는 일회용 컵 보관대 0개·후방 12개에서 E로 부족 재고를 열어 6개를 보충하고 1개를 집었다. 계량을 마친 저장으로 리드 단계부터 이어서 리드 부착·확인·전달과 5,000원 반영을 확인했다. 이때 HOT 컵 재고는 변하지 않았다. 브라우저 애플리케이션 오류는 없었고 자동 테스트 코드는 추가하지 않았다. 3026번 미리보기는 임시 모델 복사본 대신 실제 `apps/cafe`를 실행한다.

## 직접 청소와 운영 기록 확인

테이블·작업대의 자동 타이머를 직접 조작으로 바꾸고, 두 테이블의 컵·얼룩을 분리했다. 브라우저에서 컵을 든 채 저장·새로고침한 뒤 분리수거함에 옮기고, 닦기 진행 42%를 저장·복원해 완료했다. 두 번째 테이블을 정리해도 첫 번째 테이블의 컵·얼룩은 유지됐으며, 작업대·분리수거와 기존 피처 세척·선반 정리를 함께 진행했다.

청소·결산 연결을 확인한 근무에서는 콜드 브루 과다 계량 후 컵을 폐기해 실제 소비량 97.6ml가 폐기로 기록됐다. 다시 만들어 전달한 판매액 5,000원과 우유·컵·콜드 브루 준비비 14,000원을 반영해 잔액은 41,000원이었다. 개봉 후 폐기한 휘핑크림 1,000ml도 별도 기록됐다. 정리를 끝내고 결산·다음 날까지 진행하니 시작 잔액 41,000원으로 당일 기록이 초기화되고, 추출 완료한 콜드 브루 3,000ml와 만료된 초기 휘핑크림이 재고에 반영됐다.

## 컨디먼트 바와 소모품 확인

사용자 추가 요청으로 두 테이블 사이 창가에 컨디먼트 바를 배치했다. 컵 반납 90%·테이블 방치 10%, 사용한 테이블·반납대·작업대의 오염 30%를 적용한다. 확률은 전달 성공 시 한 번 계산해 게임 상태에 저장한다. 얼룩 없이 컵만 있는 자리는 회수·분리수거만으로 청소를 마친다. 손님이 걸어서 이동·착석·반납·퇴장하는 동작은 CAFE-04에서 연결했다.

추가 후 초기 상태에서 콜드 브루를 제조·전달하니 컵이 테이블에 남고 얼룩은 생기지 않는 경우가 나왔다. 냅킨·빨대는 각각 진열 20개에서 19개로 줄었다. 냅킨 100장 입고비 1,000원은 지출에 기록됐고, 1장을 집은 뒤 진열 19장·후방 199장·운반 1장 상태를 저장·복원했다. 창고에 다시 놓으면 후방 200장으로 돌아갔고, 다시 집어 실제 이동 후 컨디먼트 바에 놓으니 진열 20장·후방 199장·운반 없음으로 반영됐다. 얼룩 없는 테이블은 컵만 옮겨도 정리가 끝났다.

소모품 품절과 반납대 컵·얼룩이 있는 별도 확인용 백업도 불러왔다. 완성된 음료 전달은 품절 상태에서도 성공했고, 소모품이 음수로 줄지 않으며 보충 안내를 표시했다. 이 전달은 반납대의 컵을 2개에서 3개로 늘렸다. 세 컵을 직접 회수해 분리수거함에 옮기고 반납대를 닦아 컵 0개·오염 없음·청소 작업 없음으로 끝냈다. 브라우저에서 애플리케이션 오류는 발견하지 않았다. 확인용 백업과 캡처는 저장소 밖에 두었고 자동 테스트 코드는 추가하지 않았다.

## 손님 동선 확인

한 손님은 입구에서 POS로 이동해 도착한 뒤 주문을 받는다. 주문표 출력 후 픽업대로 이동하고, 수령 뒤 컨디먼트 이용·착석·10초 체류·컵 반납 또는 테이블 방치·퇴장을 마친다. 앞 손님이 출구에 도착해야 다음 손님 ID와 주문 번호를 만든다. 진행 단계, 경로 지점, 위치·방향, 체류 시간과 반납·오염·설탕 이용 의도를 저장한다. 매장 현황에서도 현재 손님과 이용 단계를 확인할 수 있다.

브라우저의 새 근무에서 입장 중 POS 접수가 비활성화되는 것을 확인했다. 이동 중 저장·새로고침 후 같은 손님 ID·위치·단계가 복원됐다. 콜드 브루를 직접 제조해 픽업 대기 중인 손님에게 전달했고, 반복 확인에도 판매 1잔·매출 5,000원만 기록됐다. 전달 직후에는 소모품·반납 컵이 그대로였고, 실제 컨디먼트 이용 후 냅킨·빨대가 각각 1개 줄었다.

테이블에 앉은 상태를 저장·복원하고 남은 체류 시간을 이어갔다. 이 손님은 테이블에 컵을 남기는 경우였으며, 10초 체류 후에만 컵 1개가 생겼다. 퇴장 후 새 ID의 002번 손님이 입장하고 요청은 HOT 라떼로 바뀌었다. 주문 전 마감한 두 번째 손님은 판매나 소모품 사용을 추가하지 않고 퇴장했다.

반납과 청소가 겹치는 별도 확인용 백업에서도 확인했다. 마감 중인 손님이 컵을 반납하면서 진행 중인 닦기에 새 오염이 생겼고, 닦기 확인 후 새 컵 회수 단계로 이어졌다. 컵·쓰레기를 정리하고 손님이 모두 나간 뒤 결산할 수 있었다. 다음 날에는 시작 잔액 55,000원·판매 0잔과 새 입장 상태로 이어졌고, 이전 손님의 반납이나 판매가 다시 반영되지 않았다. 브라우저 애플리케이션 오류는 발견하지 않았다.

## 첫 근무 안내와 녹음 기반 작업음

`WorkGuide`는 사용자가 H를 눌렀을 때 현재 작업의 선행 조건·도구·운반·부족 재료·라벨·보관 안내와 레시피를 보여준다. 첫 주문 진도와 자동 노출·자동 접힘은 없으며 모든 업무를 처음부터 사용할 수 있다.

음소거·음량·마우스 감도는 `preferences.ts`에서 검증하며 기존 IndexedDB의 별도 `preferences` 키에 저장한다. 게임의 `current`·`previous` 백업과 분리하고 기존 `GameState` 형식은 유지한다. 설정을 읽지 못하면 기본 음소거·음량 35%·감도 100%로 시작하며 저장 실패는 설정 화면에 표시한다.

`work-sounds.ts`는 사용자가 소리를 켜거나 근무를 시작·재개·미리 듣기 할 때 Web Audio를 활성화한다. 기본 음소거 상태에서는 오디오 컨텍스트나 음원 요청을 만들지 않는다. 현재 선택한 WAV 8개는 약 6.44MiB이며 처음 필요할 때 같은 출처에서 읽고 디코딩해 재사용한다. 단발 작업음은 최대 3개, 연속음은 1개로 제한하고 짧은 페이드를 적용한다. 얼음·완료·전달 소리는 실제 행동 전후의 변화로 결정하며, 지속음은 현재 누르기 입력이나 가까운 샷·스팀 장비 작업을 따른다.

일시정지·백그라운드·포커스 이탈·음소거·음량 0%·백업 가져오기는 재생을 중단한다. 손을 떼면 붓기·닦기 입력도 중단한다. 재개할 때는 현재 장비 작업만 다시 연결하고 저장된 지난 메시지를 재생하지 않는다. 앱 정리 시 오디오 노드·다운로드·컨텍스트도 정리하며 로딩·재생 실패는 미리 듣기로 재시도할 수 있다. 근거: [Web Audio 권장 사항](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices), [AudioContext.resume](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/resume), [AudioContext.close](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/close). 음원 출처·라이선스·가공은 [크레딧](../../apps/cafe/public/audio/CREDITS.md)에 기록한다.

브라우저에서 초기 콜드 브루를 직접 접수·계량·얼음 투입·전달했고 안내가 다음 행동으로 이어졌다. 기본 음소거 시 음원 요청이 없고, 켠 뒤 9개 음원 디코딩과 재생 노드가 생성되는 것을 확인했다. 붓기 입력 해제와 일시정지 후 연속음이 멈췄으며, 음량 60%·안내 숨김을 저장하고 새로고침해 설정과 게임 상태가 복원되는 것도 확인했다.

라떼의 우유 부족·원팩 개봉·라벨·냉장 보관, 우유 계량·스팀 완료, 폼 펌프 계량·블렌딩·라벨·보관과 두 번째 음료 전달은 저장소 밖의 확인용 백업을 불러와 수동 조작했다. 스팀 중 포커스 이탈 시 모든 음원이 종료됐고, 음량 0%에서는 계량·확인을 해도 재생 노드가 생기지 않았다. 음소거 상태의 잘못된 보관 위치 안내도 화면에 남았다. 두 번째 전달 후 안내 자동 접힘과 H 복습 열기를 확인했다. 1280×720·1024×640에서 POS 주문 버튼과 안내 배치를 확인했으며 애플리케이션 오류는 발견하지 않았다. 확인용 백업·계측·캡처는 제품 코드에 포함하지 않았다.

## 구조화 제조 자료

2026-09-25 제조 자료를 `apps/cafe/data/`의 JSON으로 정리했다. 아카데미 표에서 가져온 203개 문서와 기존 5lb 콜드 브루 배합 1개, 총 204개 문서·272개 제조 구분을 수록한다. 원래 목록은 영상 230개와 전자책 1개였으며, 영상 205개에서 표 241개를 확인했다. 중복·이전 자료 2개를 정리했고 표 미검출 영상 25개와 미변환 전자책은 `coverage.json`에 남긴다.

`recipe-schema.ts`가 Zod 구조와 행동 타입을 정의하고, `recipe-catalog.ts`는 중복 ID·재료/도구/용기 참조·사이즈별 값·범위·용기선·장비 프로그램·준비 재료 의존 관계를 검사한다. `recipe-plan.ts`는 사이즈와 컵·이용 방식·대안·물성 조건을 적용한 순서를 만든다. 한국어 메뉴명·설명 문장의 일치로 행동을 결정하던 분기는 제거했다.

현재 9개 메뉴·28개 사이즈 조합과 준비대 4종은 같은 JSON의 원문 행동을 실행한다. 콜드 브루 배치 준비는 별도 추출 업무에 연결한다. H 도움말은 현재 작업 안내와 전체 제조 자료실을 제공한다. `catalog.ts`는 현재 매장에 필요한 문서를 초기 로딩하고, `library-catalog.ts`의 전체 자료는 자료실을 열 때 별도로 읽는다.

원문 확인이 필요한 10개 제조 구분은 `review`에 질문을 남겼다. 그 밖의 정량 미기재·동작 확인 53개는 별도로 구분한다. 이 상태와 현재 게임에서 장비·작업대를 지원하는지는 다른 문제다. 원문에 수량이 없으면 미지정으로, 완성량이 없으면 null로 보존하며 장비 미구현을 원문 오류로 기록하지 않는다.

제조 계획과 표시에는 원문의 계량·순서·횟수·기간을 사용한다. 원문 없는 재혼합 3회, 얼음 3스쿱, 바모카 혼합 6초, 에스프레소 2초·스팀 5초는 제거했다. 횟수나 시간이 없는 동작은 완료 확인으로 진행한다. 원문의 폼 프로그램 약 25초와 콜드 브루 20시간은 유지한다.

`stock-amounts.ts`는 재고 차감에만 승인된 `data/simulation/stock-estimates.json`을 읽는다. 컵 선의 ml, 샷당 9g, 원문에 없는 완성 수율을 제조 기준으로 다시 사용하지 않는다. 현재 5lb·물 14L·20시간 배합의 3L는 재고 추정이며, 별도 TODDY 원문의 3lb·물 5L 후 4L·완성 6L와 섞지 않는다.

월간 갱신은 JSON 직접 수정 후 `check:recipes`·빌드로 확인한다. `dev`와 `build`도 먼저 자료 검사를 실행한다. 원본 엑셀은 참고 자료로 남겼으며 가져오기 파이프라인과 생성 파일 의존성을 제거했다. 원본 영상·이미지는 앱에 두지 않는다. 레시피 DB·버전·마이그레이션·호환 계층 없이 현재 형식 하나만 사용한다. 공개 계량 근거의 한계와 상세 운영은 [제조 자료 운영](./recipe-data.md)을 따른다.

## 날짜 기한과 배합 원재료 기한 확인

2026-09-24 사용자는 모든 N일 기한에 시작일을 포함하는 달력 계산을 적용하고, 폼·바모카의 기한을 투입한 원재료의 가장 빠른 기한으로 제한하도록 결정했다. 이때 적용한 물리 추정치 중 컵 ml·수율·원두량은 현재 별도 재고 계산에만 남겼다. 제조에 원문 없는 스팀·혼합 시간을 더하지 않는다. 세척 조작과 기한 계산의 게임 규칙은 별도로 유지한다. 원본 자료를 변경하지 않고 `Lifetime`에 일·시간 단위를 보존해 새 배치 생성·원팩 개봉에서 `expiryAt`을 호출한다. 자료 대조에서도 1일과 24시간을 같은 규칙으로 취급하지 않는다. 게임의 가상 날짜는 기존 UTC 표현을 유지하며 사용자의 PC 시간대에 영향을 받지 않는다.

재료 소비는 기존의 기한이 빠른 순서를 유지하고 실제로 사용한 양이 있는 배치들의 가장 빠른 만료 시각을 반환한다. 준비 상태의 `ingredientExpiresAt`에 누적해 원래 배치가 모두 소모돼 없어져도 저장·복원할 수 있다. 제조 완료 시 기본 만료 시각과 이 값의 최솟값을 완성 배치에 기록한다. 시간 진행에서는 장비 완료를 실제 완료 예정 시각에 처리한 다음 현재 시각의 준비 만료를 확인한다. 만료와 완료가 같으면 완성하지 않으며, 만료 전에 완성됐지만 현재 시각에는 기한이 지났다면 완성 기록과 만료된 배치를 함께 유지한다.

계량·혼합·블렌딩 중 투입 원재료가 만료되면 추가 소비와 준비 작업을 중단하고 폐기를 안내한다. 장비 작업을 제거하고 폐기할 때 이미 투입한 재료를 폐기량에 기록하며 예약한 피처를 세척 대상으로 돌려놓는다. 완성 배치의 라벨·보관도 만료를 연장하지 않는다. H 도움말에는 투입 원재료 기한을, 라벨에는 사용 불가가 시작되는 만료 시각과 원재료에 따라 짧아진 이유를 표시한다.

`ingredientExpiresAt`은 필수 nullable 필드로 새 준비에는 null로 시작하고 소비 시 기록한다. 세척 상태도 필수 nullable 필드다. 현재 형식의 검증만 수행하며 누락 필드 처리나 레거시·버전별 분기·마이그레이션·호환 코드는 두지 않는다.

날짜 계산은 9월 1일 15시 개봉 우유 → 9월 3일 0시, 7일 기한 원두 → 9월 8일 0시, 24시간 휘핑크림 → 9월 2일 15시를 확인했다. 월말과 윤년의 2월 29일을 지나는 경우도 확인했다. 브라우저에서 우유 원팩을 실제로 개봉하니 9월 3일 00:00 라벨과 날짜 기준 설명을 표시했다.

브라우저에서 10시 만료 크림 100ml와 11시 만료 크림 300ml가 있는 확인용 백업을 불러와 약 200ml를 계량했다. 먼저 쓰인 100ml 배치가 사라진 뒤 저장·새로고침해도 준비의 10시 기한은 유지됐다. 우유·7펌프·블렌딩까지 마친 폼 450ml의 만료 시각도 10시였고 원재료 기한 설명을 표시했다. 별도 만료 상황에서는 블렌딩이 중단됐고 F로 폐기한 뒤 크림 200ml·우유 50ml·소스 71.4ml가 폐기로 기록됐으며 피처가 세척 대상으로 돌아갔다. 완료보다 먼저·동시에 만료되는 경우, 완료 직후 현재 시각 전에 만료된 경우도 확인했다. 확인용 데이터는 저장소 밖에 두었고 테스트 코드는 추가하지 않았다.

## 용기 운반과 콜드 브루 직접 준비

2026-09-25 사용자 확인에 따라 준비대에서 라벨을 붙인 뒤 용기를 직접 운반한다. 배치 위치에 준비대·추출대·손을 구분하고 E 집기·원래 자리로 반납·냉장고/실온 선반 보관을 연결했다. 이동은 기존 배치의 위치만 변경한다. 라벨·만료·배치 ID·수량을 새로 만들지 않으며 보관 전에는 사용 가능 재고에 포함하지 않는다. 원팩은 창고에서 개봉·라벨·보관한다. 원격 라벨·보관·폐기를 차단하고 한 용기만 운반하며 다른 물건과 동시 소지를 막는다.

콜드 브루는 별도 `coldBrew` 상태에 계량 단계·진행량·도구·원두/물 투입량·추출 완료 시각·회수 배치 ID를 저장한다. 준비비 9,000원으로 한 배치분을 확보하며 원두는 한 봉 5lb에서 멈추고 물 14L는 ±6% 허용 구간을 사용한다. G로 도구를 집고 누르며 계량한 뒤 도구를 놓고 F로 확인한다. Space로 20시간 추출 작업을 만들며 완료 시에는 재고를 늘리지 않고 회수 대기로 바꾼다. E로 회수할 때 3L 배치를 한 번 만들고 추출 완료 시각부터 기한을 계산한다. 라벨·집기·냉장 운반이 끝나면 준비 상태를 비운다.

계량 중·회수 대기·운반 상태는 마감 전에 마무리하거나 폐기해야 한다. 추출 중에는 마감할 수 있고 다음 날 이동 시 실제 완료 예정 시각으로 회수 대기에 들어간다. 중단 전에는 원두 한 배치분, 추출 완료 후에는 완성 추출액으로 폐기를 기록해 중복 집계를 피한다. 준비비는 입고 지출로 남는다. 새 작업대·실온 선반을 직원 통로 뒤쪽에 배치하고 용기·도구 표현, 조작 안내와 작업음을 연결했다.

현재 저장 형식만 검증한다. `ingredientExpiresAt`·`washing`의 누락 허용과 기한 기록 누락 처리, 자료 JSON의 버전 필드를 제거했다. 새 콜드 브루 상태·폐기 기록도 필수이며 누락 데이터를 보완하는 코드나 버전별 분기는 없다. 운반 용기 하나 제한, 동시 소지 제한, 용기와 준비 상태 연결, 추출 작업과 준비 ID 연결을 저장 검증에 포함한다.

브라우저에서는 현재 형식의 확인용 백업에서 콜드 브루 원두 5lb·물 약 14.17L를 직접 계량했다. 운영비는 50,000원에서 41,000원이 됐고 추출 시간이 20시간으로 기록됐다. POS에서 마감·다음 날을 진행하니 DAY 02 05:00 완료 시각으로 회수 대기에 들어갔다. 회수·라벨 후 3L 용기를 든 채 저장·새로고침했으며 같은 ID·잔량·라벨·9월 9일 0시 만료 시각이 유지됐다. 냉장고에 보관한 뒤 준비 상태와 손이 비워지고 3L 배치 한 개만 사용 가능 재고에 추가됐다. 제조 완료는 한 번, 보관도 한 번 반영됐다.

## 호지 글레이즈드 티 라떼 HOT·ICED

2026-09-25 사용자가 고른 한 종류의 메뉴를 두 온도로 확장했다. 메뉴·온도별 클래식 시럽 펌프 수와 7.5ml 용량, 파우더 2톡을 자료에 연결했다. 호지차 샷 준비는 정수 250ml·1티스푼 스쿱 8회·쉐이킹 10회를 의미와 단위로 연결하며, 준비 자료의 냉장·24시간을 사용한다. 클래식 시럽은 코어 품질 표의 개봉 후 1개월·실온을 연결했다. 자료 검사는 음료 5개와 준비 4종·품질 10개를 확인한다.

준비 상태에 파우더 투입량과 계량/쉐이커 도구를 추가하고 기존 라벨·기한·운반·폐기 흐름을 사용한다. 컵에는 호지차 층과 사용 전 재혼합 완료 상태를 저장한다. 원문대로 사용 전 혼합 완료를 확인하며 재혼합 횟수는 지정하지 않는다. 혼합 자체는 재고를 소비하지 않는다. HOT은 기존 우유 스팀을, ICED는 우유 직접 붓기·얼음을 사용한다. 에스프레소 추출·샷 이관·바모카 드리즐 단계는 없다. 준비대 선택, 부족 재료 안내, 작업 HUD, 도구/컵 표현과 메뉴판을 함께 연결했다. 새 저장 필드도 필수이며 이전 형식 변환·누락 보완은 추가하지 않았다.

원문에서 비어 있는 ml와 완성 수율은 현재 제조 데이터에 추정해서 넣지 않는다. 기존 재고 규격·수율·가격은 제조 기준과 분리하고 재혼합 횟수는 제거했다. 달력 한 달 해석과 신규 임시값은 추가 사용자 확인 전 제안값이다. 9월 25일 → 10월 25일 0시, 1월 31일 → 3월 1일 0시, 윤년과 연말의 월 계산을 확인했다.

브라우저에서는 초기 재고를 유지하고 손님 요청만 호지 HOT으로 설정한 현재 형식의 확인용 백업으로 시작했다. 우유·클래식 시럽·호지차 파우더를 개봉·라벨·보관하고, 정수 약 246.8ml·파우더 8스쿱·10회 쉐이킹으로 샷 250ml를 만들었다. 라벨 후 냉장고까지 직접 운반해 제조 후 24시간 기한과 사용 가능량을 확인했다. 폼도 직접 계량·블렌딩·운반하고 피처 한 개를 세척·선반 정리했다. 준비 완료 뒤 확인용 브라우저가 응답하지 않아 재실행하고 내보낸 현재 형식의 백업에서 이어갔다.

## 매장·포장 컵과 작업 UI 연결

2026-09-25 사용자 확인에 따라 매장·포장 주문을 50%씩 생성하고, HOT 종이컵·ICED 일회용 컵·HOT 머그·ICED 유리잔을 구분했다. POS·주문표에 이용 방식을 표시하고 메뉴와 컵 종류를 함께 대조해 전달한다. 매장용은 종류별 4개를 회수·직접 세척·컵 보관대 반납 후 다시 쓰며, 포장용은 종류별 보관대 2개·후방 12개와 별도 보충·입고를 관리한다. 매장용 재제조는 내용물만 폐기하고 컵을 세척 대상으로 보낸다. 포장 손님은 소모품 이용 후 컵을 들고 퇴장한다.

## 빌드 청크 분리

2026-09-25 사용자가 500KB 초과 경고 해결을 요청했다. Vite 8.3.0의 빌드 모듈 구성을 확인한 결과, 메인 청크에는 React·React DOM·scheduler와 앱 코드·Zod·자료가 함께 들어 있었고, 동적 장면 청크에는 Three.js의 `three.core.js`와 `three.module.js`, 앱의 3D 코드가 함께 들어 있었다.

`apps/cafe/vite.config.ts`의 `build.rolldownOptions.output.codeSplitting.groups`에서 React 계열, Three.js 코어, Three.js 렌더러를 각각 분리한다. Three.js 코어 그룹을 렌더러보다 먼저 선언해, 기본 의존성 포함 동작이 두 모듈을 다시 합치지 않도록 한다. 앱 코드는 기존 자동 청크 분리를 사용한다. [Vite 빌드 옵션](https://vite.dev/config/build-options#build-rolldownoptions), [Rolldown 청크 분리](https://rolldown.rs/reference/OutputOptions.codeSplitting)

별도 라이브러리 청크는 앱 코드가 바뀔 때 함께 갱신되는 캐시 범위를 줄인다. 생성된 정적 의존성에서 React는 bundler runtime만, Three.js 렌더러는 Three.js 코어만 참조한다. 이 라이브러리들이 앱 청크를 참조하는 순환은 없다. `includeDependenciesRecursively`는 기본값을 유지하며, 원본 모듈 경계로 분리한다.

3D 로딩 시점은 기존처럼 시작 화면을 준비할 때의 `import('../game/scene')`다. 초기 HTML은 React와 bundler runtime을 preload하고, 장면의 동적 import가 Three.js 코어·렌더러를 함께 불러온다. 게임 규칙·저장 형식·React 화면 구조·엔진·의존성 버전은 변경하지 않았다.

| 청크            |   변경 전 바이트 | 변경 후 바이트 | 변경 후 gzip 바이트 |
| --------------- | ---------------: | -------------: | ------------------: |
| 메인            |          520,844 |        330,497 |              81,563 |
| 장면            |          584,274 |         42,475 |              16,708 |
| React 계열      |      메인에 포함 |        189,588 |              59,604 |
| Three.js 코어   |      장면에 포함 |        191,004 |              51,880 |
| Three.js 렌더러 |      장면에 포함 |        352,317 |              84,771 |
| Bundler runtime | 기존 청크에 포함 |            589 |                 368 |

수치는 minify한 실제 출력 파일의 UTF-8 바이트 길이다. 가장 큰 청크는 584,274바이트에서 352,317바이트로 줄었다. `chunkSizeWarningLimit` 변경이나 경고 필터 없이 Vite 기본 500KB 기준을 통과한다.

JS 파일은 2개에서 6개가 되고, 전체 JS 크기는 1,105,118바이트에서 1,106,470바이트로 거의 같다. 이번 변경은 개별 청크와 캐시 경계를 정리한 결과다. 전체 전송량 감소나 실행 중 프레임 속도 향상을 의미하지 않는다.

`bun run --filter=@sobok/cafe build`의 자료 검사·타입 검사·프로덕션 빌드와 설정의 Biome 검사를 통과했고, 청크 크기 경고는 발생하지 않았다. 프로덕션 미리보기의 별도 브라우저에서 여섯 JS 파일의 HTTP 200 응답, 1280×720 시작 화면과 3D 장면, POS 주문 접수, 도움말 진입·복귀, 컵 집기·이동·콜드 브루 계량·확인, 저장 후 새로고침·이어 하기를 확인했다. 브라우저 오류와 콘솔 오류는 없었다.

자동 테스트나 분석용 제품 코드는 추가하지 않았다. 모듈 분석 결과와 화면 캡처는 저장소 밖에 보관하고, 확인용 브라우저·서버는 종료했다.

## 메뉴 가격과 사이즈

타입 검사·자료 연결 검사·프로덕션 빌드를 확인했다. 브라우저에서 사이즈별 POS 가격 전환, 요청과 다른 주문 표시, Grande 머그의 사용 가능 재고 감소, 공통 세척 조작과 보관 후 같은 사이즈 재고 복귀, 저장 데이터 반영을 확인했다. Trenta의 887ml·6,900원 표시와 매장 주문·다른 메뉴로 전환할 때 Trenta가 사라지고 Tall로 돌아가는 동작도 브라우저에서 확인했다. 자동 테스트 코드는 추가하지 않았다.
